## 0. 先说结论（TL;DR）

1. 圣域群系**不是**通过"改注册表/改维度参数表"挂进主世界的。群系 JSON 只负责被正常加载进 `BIOME` 注册表；**真正让主世界用上它的是三处运行时钩子**：`possibleBiomes()` 注入 + `getNoiseBiome()` 注入 + **区块 biome 调色板物理重写**。
2. 🔴 **圣域确实调用了 `possibleBiomes()`**（`BiomeSourceMixin.java:42`），这与长城的冻结红线 R3 **直接冲突**。必须如实报告：圣域的做法**就是**长城禁止的那一种。
3. 🔴 **本报告的新增量：那两处 BiomeSource 注入在存在包装器（Lithostitched `InjectorBiomeSource`）时双双不成立**（已用字节码定出"包装早于 `LOAD`"的时序），真正扛住"群系真的出现在世界里"的是 `SanctuaryBiomeWriter`——一个**不碰 `possibleBiomes`、不碰 `getNoiseBiome` 的纯区块调色板重写**。这条路径与长城 R3 **不冲突**。
4. ⚠️ **但"只抄路径 C"不足以让长城群系的植被长出来**：`retainAll` 会把不在 `possibleBiomes()` 里的群系剔除（与 `_查证-群系时序与注入点-20261006.md` §7.2 结论一致）。因此本报告给出的「长城实现模板」**只采用路径 C 做群系写入，并明确要求植被由长城自己的写入路径承担**（§7.3 出路 1）。

## 1. 问题一：群系怎么"注入"世界的？

### 1.1 结论

圣域用的是**运行时注入**，不是"注册新群系就自动生成"。分三条独立路径，**强弱与风险完全不同**：

| # | 路径 | 实现位置 | 作用面 | 与长城 R3 关系 |
|---|---|---|---|---|
| A | `BiomeSource#possibleBiomes()` RETURN 注入 | `mixin/BiomeSourceMixin.java:40-52` | 影响"这个 BiomeSource 有哪些群系可用" | ❌ **直接违反 R3** |
| B | `MultiNoiseBiomeSource#getNoiseBiome()` HEAD 注入 | `mixin/MultiNoiseBiomeSourceMixin.java:25-36` | 直接改写气候采样选群系的结果 | ✅ 形式上不碰 R3 |
| C | **区块 biome 调色板物理重写** | `SanctuaryBiomeWriter.java:15-58` | 已生成区块的 4×4×4 quart 群系格子 | ✅ 完全不碰 BiomeSource 查询 |

**路径 C 是被低估的主角**。下面逐条给证据。

### 1.3 `possibleBiomes()` 到底影响什么（vanilla 一手证据）

【javap】`net.minecraft.world.level.biome.BiomeSource`：`possibleBiomes()` 是一个 **Guava memoize 的懒求值 Supplier**：

```
private final Supplier<Set<Holder<Biome>>> possibleBiomes;      // 字段
protected BiomeSource();                                         // 构造器
   4: aload_0
   5: aload_0
   6: invokedynamic #51   // get:(BiomeSource)Supplier
  11: invokestatic  #57   // com/google/common/base/Suppliers.memoize
  14: putfield      #59   // Field possibleBiomes
public Set<Holder<Biome>> possibleBiomes();
   1: getfield #59
   4: invokeinterface Supplier.get
```
→ **首次调用后结果被永久缓存**（该实例生命周期内）。这一点是本报告第 3 节的关键。

全 jar 扫描【javap】常量池，`possibleBiomes` 只出现在 7 个类：
`BiomeSource`、`CheckerboardColumnBiomeSource`、`FixedBiomeSource`、`MultiNoiseBiomeSource`、`TheEndBiomeSource`、`ChunkGenerator`、`ChunkGeneratorStructureState`。

其中 **`ChunkGenerator` 的调用点有两处**：

1. **`ChunkGenerator.applyBiomeDecoration`**（不是 `buildSurface`！）——对区块 biome 集合做 `retainAll(possibleBiomes())`：

> 🔴 **对圣域注释的一处更正**：`BiomeSourceMixin.java:26-27` 自述"`NoiseBasedChunkGenerator#buildSurface` 会调用 `biomeSource.possibleBiomes()` 并对其结果做 `retainAll`"。

> **真正做 `retainAll(possibleBiomes())` 的是 `ChunkGenerator.applyBiomeDecoration`。** 圣域注释把位置写错了；结论方向（污染集合会让特征阶段失效）仍然成立，但机制位置必须更正。

### 1.5 路径 C：`SanctuaryBiomeWriter` 区块调色板重写（真正的兜底）

`SanctuaryBiomeWriter.java:15-58`（全文 59 行，见第 3 节逐行拆解）。
调用点有**两个**：

- `ChunkGeneratorMixin.java:25-33` — `applyBiomeDecoration` **HEAD**，在特征阶段开始前把 biome 写回去；
- `GoldenErdtreeSanctuaryMod.java:121-125` — `ServerChunkEvents.CHUNK_LOAD`，兜底重写从磁盘读入的区块。

> 这一点是圣域设计的核心机智之处：**即使 BiomeSource 注入因任何原因（包装器、memoize、维度判定）失效，区块级重写仍会把群系落到世界上**。第 3 节会说明这条路径为何是"不得不重写"。

### 1.6 ⚠️ 与 Lithostitched 包装器的交互（**本报告最高价值发现**）

实机 mods 目录存在 `lithostitched-1.8.0+beta6-fabric-21.1.jar`（`docs/evidence/s0-01/environment.json:81`）。

【javap】对该 jar：

而圣域注册的正是**包装器实例**（`GoldenErdtreeSanctuaryMod.java:92-93` 取 `getBiomeSource()`，即外层 `InjectorBiomeSource`）。

于是产生**两个很可能同时成立的失效**：

| 注入点 | 门禁 | 在包装场景下的判定 | 后果 |
|---|---|---|---|
| `BiomeSourceMixin:44` | `this instanceof MultiNoiseBiomeSource` | 外层 `InjectorBiomeSource` **不是** `MultiNoiseBiomeSource` → `return` | 注入不发生 |
| `BiomeSourceMixin:46` | `isOverworldSource(this)` | 即使换到内层 MNBS 上判定，内层**从未被登记** → `false` → `return` | 注入不发生 |
| `MultiNoiseBiomeSourceMixin:31` | `isOverworldSource(this)` | 内层 MNBS 未被登记 → `false` → `return` | 注入不发生 |

**【推导，未运行验证】** 在 Lithostitched 包装存在的实战包里，路径 A、B **可能双双是空操作**，世界里的圣域群系完全由路径 C（`SanctuaryBiomeWriter`）产生。

**这个推导有一条重要的限定（避免过度断言）**：
- 路径 B（`MultiNoiseBiomeSourceMixin`）注入的是**内层** `MultiNoiseBiomeSource#getNoiseBiome`。它的 `isOverworldSource(this)` 门禁看的是**内层实例**，而登记的是**外层包装器** → 门禁失败 → **路径 B 确定失效**（这条推断很硬，因为 `this` 与登记对象必然是不同实例）。
- 路径 A（`BiomeSourceMixin` 注入 `BiomeSource#possibleBiomes`）门禁之一是 `this instanceof MultiNoiseBiomeSource`。**外层 `InjectorBiomeSource` 不满足**。但注意 `@Mixin(BiomeSource.class)` 会应用到**所有** `BiomeSource` 子类，包括内层 MNBS —— 内层虽然也走这个 mixin，却卡在 `isOverworldSource(内层) == false`。→ **路径 A 在外层、内层两侧都不成立**。

**⚠️ 但这与 T1 的分析存在张力，必须一起读**：`SanctuaryRuntime.java:21-25` 的注释声称"已由日志实证：主世界/营地维度各一个 `InjectorBiomeSource` 包装"。如果这个"日志实证"是真的，那么圣域**应该早就发现注入无效**——除非包装发生在 `LOAD` 之后。**本次已把这条时序查清**：

**【javap】Lithostitched 的包装触发点（决定性证据）**

- `class_3176` = **`net.minecraft.server.dedicated.DedicatedServer`**
- `method_3735` = **`loadLevel`**（`:98189`，enclosing class = `MinecraftServer`）

即 Lithostitched 注入的是 **`DedicatedServer.initServer` 中调用 `loadLevel()` 之前**。

⇒ **Lithostitched 的包装确实早于 `LOAD`**。所以圣域 `GoldenErdtreeSanctuaryMod.java:92-93` 登记到的 `getBiomeSource()` **就是外层 `InjectorBiomeSource`**（与圣域注释的自述一致），而：
- `BiomeSourceMixin:44` 要求 `this instanceof MultiNoiseBiomeSource` → 外层不满足；
- 内层 MNBS 虽也过同一 mixin，但卡在 `isOverworldSource(内层) == false`；
- `MultiNoiseBiomeSourceMixin:31` 同样卡在内层身份白名单。

⇒ **§1.6 的推导在时序上成立，且不依赖任何未验证假设。**

**仍然保留的唯一不确定性**：`ServerWorldEvents.LOAD` 是否会**再次**触发（例如维度重新加载）而在某个时刻登记到内层实例；以及除 Lithostitched 外的其它路径是否会产生未包装的 MNBS 实例。这两点**未验证**，因此 §1.6 仍标【推导】。

**给长城的行动项（实机二分，未执行）**：
在圣域内定位一处**只有该群系 features 才会产生**的方块（例如 `flower_meadow` 的矢车菊/郁金香，或 `patch_grass_plain` 的草丛），记录密度；然后**禁用 Lithostitched** 再测一次。
- 若禁用后密度**上升** → §1.6 成立（包装器确实压制了注入）；
- 若两次**无差异** → 注入本来就没生效（T1 成立），或注入与包装器无关。

## 2. 问题二：`SanctuaryRuntime` 的线程安全设计

`SanctuaryRuntime.java` 全文 184 行。四个静态状态：

### 2.1 为什么用 `Climate.Sampler` 而不是别的东西做 key？

**因为它是唯一"随维度天然唯一、且能一路传到注入点"的句柄。**

- 【javap】`Climate$Sampler` 是 **record**：`public final class net.minecraft.world.level.biome.Climate$Sampler extends java.lang.Record`，带 `equals`/`hashCode`。
- 它的来源是 `RandomState`：`ChunkGeneratorMixin.java:47-49` 走 `level.getLevel().getChunkSource().randomState().sampler()`；`NoiseBasedChunkGeneratorMixin.java:24` 走 `randomState.sampler()`。
- 【javap】`ServerChunkCache.randomState()` 直接转发 `ChunkMap.randomState()`，而 `RandomState` 是**每个维度各一份**的 ServerLevel 级对象。

所以：**sampler 身份 ≈ 维度身份**，用一个 key 同时解决"这是哪个维度"和"我该用哪套 layout"两个问题。

**为什么用 `IdentityHashMap` 而不是普通 `HashMap`（明明 record 有 equals）？**
`SanctuaryRuntime.java:31-32` 给了理由：*"BiomeSource 未重写 equals/hashCode，且我们就是要按实例身份区分维度"* —— 但那句注释是针对 `OVERWORLD_SOURCES` 的。对 `CONTEXTS` 而言，用 `IdentityHashMap` 是**刻意的保守选择**：避免两个结构相等但语义不同的 `Sampler`（例如同一 seed 在两个隔离测试世界里各建一份 `RandomState`）互相覆盖。**取值的所有路径也一律用 `==` 比较实例身份**（`:87`、`:91`），与 `IdentityHashMap` 的语义自洽。这是一个"宁可查不到，也不串维度"的 fail-closed 设计。

> **对照长城**：长城 `terrain/CpuTerrainOracle.java` 里保存 `biomeSource` 并只调 `getNoiseBiome`（`docs/S1-S5实施规格/S1-城墙本体.md:1064`、`:1078`），同样用 sampler 作为"这是哪个维度/哪份 RandomState"的锚。**这条设计可以直接照搬**。

### 2.2 `contextSnapshot` / `lastLookup` 的 volatile 快照模式

```java
:85  public static Context get(Climate.Sampler sampler) {
:86      SamplerContext cached = lastLookup;
:87      if (cached != null && cached.sampler() == sampler) {
:88          return cached.context();
:89      }
:90      for (SamplerContext entry : contextSnapshot) {
:91          if (entry.sampler() == sampler) {
:92              lastLookup = entry;
:93              return entry.context();
:94          }
:95      }
:96      return null;
:97  }

:113 private static void rebuildSnapshot() {
:114     contextSnapshot = CONTEXTS.entrySet().stream()
:115             .map(entry -> new SamplerContext(entry.getKey(), entry.getValue()))
:116             .toArray(SamplerContext[]::new);
:117     lastLookup = null;
:118 }
```

**设计要点（逐条）：**

1. **写侧串行化**：`register`（`:66`）/`unregister`（`:80`）都是 `synchronized`，且都调 `rebuildSnapshot()`。`CONTEXTS` 本身只在锁内被触碰 → **读线程从不直接读 `IdentityHashMap`**。
2. **发布不可变数组**：`contextSnapshot` 是一个**全新分配的数组**（`:116`），元素 `SamplerContext` 是 record（不可变）。`volatile` 写保证：**数组引用的发布 happens-before 后续 `volatile` 读**，因此读线程看到数组引用非 null 时，数组**全部元素**都已正确构造可见。这是标准的 copy-on-write + volatile 发布。
3. **读侧无锁**：`get` 完全不加锁（`:85-97`），适合 worldgen 高频调用。读到的是某一时刻的一致快照——**要么全旧、要么全新，不会撕裂**。
4. **`lastLookup` 是单元素缓存**：worldgen 单线程在一次区块生成中会连续调用成千上万次、且 sampler 恒定，`lastLookup` 把 O(n) 数组扫描降到一次 `==` 比较。**它自身也是 volatile**（`:16`），所以别的线程写它不会造成可见性问题；`rebuildSnapshot` 后置 null（`:117`）防止指向被移除的 context。
5. **`lastLookup` 的良性竞态**：多个 worldgen 线程同时命中不同 sampler 时会互相覆盖 `lastLookup`，但那只导致缓存未命中退化到数组扫描，**不影响正确性**。
6. **`SANCTUARY_BIOMES` 用 `synchronizedSet` + `Set.copyOf` 读出**（`:40`、`:107-111`）：`biomes()` 返回值拷贝，调用方拿不到内部集合，避免遍历期间被并发修改。

> **与长城规则的对照**：长城 R2 要求"跨线程公开值仅不可变对象、`ConcurrentHashMap` 和它承载的 promise"（`docs/S1-S5实施规格/README.md:39`）。圣域这里是 **"`synchronized` 写 + volatile 不可变数组快照 + 无锁读"**，与 R2 的**精神完全一致**（对外只暴露不可变快照），只是容器换成了 `IdentityHashMap` + 数组。**这个模式可以照搬**，但要注意：`rebuildSnapshot` 的 `stream().map().toArray()` 有分配成本，只在 LOAD/UNLOAD 触发，不在热路径。

**因为 vanilla 根本不提供 `setBiome`。**

【javap】`net.minecraft.world.level.chunk.LevelChunkSection` 的**全部** public 方法（原文列表）：

### 3.3 `QuartPos` 的坐标换算（群系是 4×4×4 quart 分辨率）

【javap】`net.minecraft.core.QuartPos` 全部方法（逐字节码）：
```
fromBlock(v)     = v >> 2          // block → quart（向下取整，负数正确：-1>>2 = -1）
toBlock(v)       = v << 2          // quart → block
quartLocal(v)    = v & 3           // 取 quart 在所属 4×4×4 格子内的局部下标 0..3
fromSection(v)   = v << 2          // section Y → quart Y（section 底部的 quart）
toSection(v)     = v >> 2
BITS=2, SIZE=4, MASK=3
```

**一个区块 = 16×16 方块 = 4×4 quart（XZ）**；**一个 section = 16 高 = 4 quart（Y）**。

`SanctuaryBiomeWriter.apply` 的换算链条：

| 步骤 | 代码 | 含义 |
|---|---|---|
| 区块最小 block 坐标 → quart | `:26-27` `QuartPos.fromBlock(minX/minZ)` | 该区块左下角的 quart 坐标（`minX` 必为 16 的倍数 → `>>2` 精确） |
| 预算 4×4 个 quart 列 | `:28-34` 双层循环 + `QuartPos.toBlock(quartX + localQuartX)` | `:31` 把每个 quart 列换回 **block** 坐标（`<<2`）交给 `context.biomeAt`，因为 `biomeAt` 吃 block 坐标 |
| 每 section 的 quart Y | `:40-41` `int sectionY = chunk.getMinSection() + sectionIndex; int quartY = QuartPos.fromSection(sectionY);` | section 底部的 quart Y |
| 回调收到的坐标 | vanilla 传入 `quartX + lx`, `quartY + ly`, `quartZ + lz`（**绝对 quart 坐标**，lx/ly/lz ∈ 0..3） | 见 【javap】`LevelChunkSection.fillBiomesFromNoise` 偏移 `50: iload_3; 51: iload 8; 53: iadd` 等 |

> **关键点**：`quartLocal(v) = v & 3` 对**负坐标同样正确**（`-1 & 3 = 3`、`-5 & 3 = 3`）。这是它能直接用掩码而不是取模的原因，也是这段代码能正确处理负 X/Z 区块的根本。**抄的时候不要换成 `% 4`**（Java 的 `%` 对负数返回负数，会数组越界/取错列）。

四个文件的第 9 槽只有：草丛（`patch_grass_*`、`patch_tall_grass*`）、花（`flower_meadow`、`flower_forest_flowers`）、甘蔗（`patch_sugar_cane`）、大蕨（`patch_large_fern`）、自家石头（`sanctuary_mossy_rock`）、BOP 花。**没有任何 `minecraft:trees_*`、`minecraft:oak_checked`、`birch` 等**。

这直接生效，因为【javap】`applyBiomeDecoration` 放置 feature 的唯一依据就是 `generationSettingsGetter.apply(biome).features()`（偏移 `447-460`）——**该区块内某群系的 features 列表为空，该群系在这个 step 就什么都不长**。

**并且 `:1523` 级别的"没有别的树来源"也成立**：圣域 mod 内**没有任何针对 `TreeFeature` 的 Mixin**（本次对 `src/main/java` 全量 grep `TreeFeature|tree.*Mixin|cancel|setReturnValue(false)`，只命中 `BiomeSourceMixin.java:42` 与 `MultiNoiseBiomeSourceMixin.java:27` 这两处 BiomeSource 注入）。所以"不长树"**纯粹靠数据（features 列表留空）**，不靠代码拦截。

## 5. 问题五：它怎么防止别的 mod 在圣域里长树？

### 5.1 结论：**只有"群系 features 列表"这一层，没有额外机制。**

本次做了三轮取证，结论是"没有别的机制"：

| 排查项 | 结果 |
|---|---|
| `src/main/java` 内是否有 `@Mixin(TreeFeature.class)` 或任何树拦截 | **无**。全量 grep `TreeFeature` → 0 命中 |
| 是否有 `setReturnValue(false)` / `callback.cancel` 式拦截 | **无**。全量 grep → 仅 `BiomeSourceMixin.java:42`、`MultiNoiseBiomeSourceMixin.java:27`（都是 BiomeSource 注入，非树拦截） |
| 是否有"事后删树"逻辑 | **仅限河道**：`SanctuaryTerrainFinalizer.java:367` 的 `isHydrologyCover` 里包含 `state.is(BlockTags.LOGS) \|\| state.is(BlockTags.LEAVES)`，但它**只在 `sealHydrology` 的水道柱清空逻辑里被调用**（`:333-335`），作用范围是河流/湖泊水面以上，**不是通用防树** |

### 5.2 那"别的 mod 不长树"靠什么成立？

靠 **两条 vanilla 事实**：

1. **特征放置是"按群系查表"的**。【javap】`ChunkGenerator.applyBiomeDecoration` 偏移 `447-460`：只对**该区块实际存在的群系**调 `generationSettingsGetter.apply(biome).features()`。圣域群系的 `BiomeGenerationSettings` 来自圣域自己的 JSON → `features[9]` 为空 → **原版/其他 mod 注册在"森林/平原"等群系上的树，不会因为位置在圣域而长出来**。
2. **区块的 biome 被物理改写了**（§3）。别的 mod 走 `getNoiseBiome` 或读区块 biome 决定放什么时，看到的也是圣域群系。

### 5.3 ⚠️ 这套防御的三个漏洞（**必须让长城知道**）

| 漏洞 | 说明 | 证据 |
|---|---|---|
| **V1. 全局 feature 注入型 mod** | 若某 mod 用 `BiomeModification`/全局 placed_feature 的方式（不按群系绑定）注入树，群系列表挡不住 | **未验证**。本次未枚举实机 mod 的注入方式 |
| **V2. 结构型巨树** | jigsaw 结构按自己的 `biomes` 白名单放，不看 `features` 列表 | 圣域自己就靠这条绕过了 §5.2（`gna_giant_oak_tree.json:13-16`） |
| **V3. `possibleBiomes` 失效时连自家 features 也没了** | 若 §1.6 的推导成立，`retainAll` 会把圣域群系剔掉，**圣域自己的草丛/花也不长**（这反而是"更彻底的不长树"） | 【推导】，见 §1.6 |

> **对长城的直接含义**：长城已经有 `mixin/TreeFeatureMixin.java:15-33` 这层**主动**拦截（`services.vegetation().intersects(...)` → `setReturnValue(false)`），这是圣域**没有的**、也**比圣域更强**的一层。**长城不应该为了抄圣域而删掉自己的 TreeFeatureMixin**——两者的关系是"圣域=被动数据防御，长城=主动代码防御"，长城是超集。

**（b）运行时表 `GreatWallBiomeRuntime`**（照搬 `SanctuaryRuntime` 的快照模式，**但不含 `OVERWORLD_SOURCES`**）：

```java
public final class GreatWallBiomeRuntime {
    private static final Map<Climate.Sampler, WallBiomeContext> CONTEXTS = new IdentityHashMap<>();
    private static volatile SamplerContext[] contextSnapshot = new SamplerContext[0];
    private static volatile SamplerContext lastLookup;

    public static synchronized void register(Climate.Sampler s, WallBiomeContext c) {
        CONTEXTS.put(s, c); rebuildSnapshot();
    }
    public static synchronized void unregister(Climate.Sampler s) {
        CONTEXTS.remove(s); rebuildSnapshot();
    }
    private static void rebuildSnapshot() {           // 只在 LOAD/UNLOAD 调用，不在热路径
        contextSnapshot = CONTEXTS.entrySet().stream()
                .map(e -> new SamplerContext(e.getKey(), e.getValue()))
                .toArray(SamplerContext[]::new);
        lastLookup = null;
    }
    public static WallBiomeContext get(Climate.Sampler s) {   // 无锁读
        SamplerContext cached = lastLookup;
        if (cached != null && cached.sampler() == s) return cached.context();
        for (SamplerContext e : contextSnapshot) {            // volatile 数组 = 一致快照
            if (e.sampler() == s) { lastLookup = e; return e.context(); }
        }
        return null;                                          // ← null 即"不是长城维度"
    }
    private record SamplerContext(Climate.Sampler sampler, WallBiomeContext context) {}
}
```

**（c）核心写入器 `GreatWallBiomeWriter`**（照搬 `SanctuaryBiomeWriter`，改判据）：

```java
public static boolean apply(ChunkAccess chunk, Climate.Sampler sampler, WallLayout layout,
                            Holder<Biome> wallBiome) {
    int minX = chunk.getPos().getMinBlockX();
    int minZ = chunk.getPos().getMinBlockZ();
    if (!layout.intersectsChunk(minX, minZ)) return false;   // 早退：区块不碰长城走廊

    // ① 预算 4×4 quart 列（每列只算一次，避免在回调里重复求值）
    Holder<Biome>[] columns = new Holder[16];                // null = 保持原群系
    int quartX = QuartPos.fromBlock(minX);
    int quartZ = QuartPos.fromBlock(minZ);
    for (int lz = 0; lz < 4; lz++)
        for (int lx = 0; lx < 4; lx++)
            if (layout.containsWallBiome(              // ← 长城的判据：走廊 + 缓冲带
                    QuartPos.toBlock(quartX + lx),     //    返回 block 坐标（<<2）
                    QuartPos.toBlock(quartZ + lz)))
                columns[lx + lz * 4] = wallBiome;

    // ② 逐 section 借用官方唯一写入口
    LevelChunkSection[] sections = chunk.getSections();
    for (int i = 0; i < sections.length; i++) {
        LevelChunkSection section = sections[i];
        PalettedContainerRO<Holder<Biome>> original = section.getBiomes();
        int sectionY = chunk.getMinSection() + i;
        int quartY   = QuartPos.fromSection(sectionY);        // section 底的 quart Y
        section.fillBiomesFromNoise((qX, qY, qZ, ignored) -> {
            Holder<Biome> w = columns[QuartPos.quartLocal(qX)      // v & 3，负数也正确
                                    + QuartPos.quartLocal(qZ) * 4];
            if (w != null) return w;
            return original.get(QuartPos.quartLocal(qX),          // 范围外原样回读
                                QuartPos.quartLocal(qY),
                                QuartPos.quartLocal(qZ));
        }, sampler, quartX, quartY, quartZ);
    }
    chunk.setUnsaved(true);
    return true;
}
```

**（d）注入点**（`applyBiomeDecoration` HEAD，与 `ChunkGeneratorMixin.java:25-33` 同构）：

```java
@Inject(method = "applyBiomeDecoration", at = @At("HEAD"))

                                   StructureManager structures, CallbackInfo ci) {
    if (level.getLevel().dimension() != Level.OVERWORLD) return;      // 维度门禁（硬比较，不用白名单）
```

**（e）注册时机**（`ServerWorldEvents.LOAD` / `UNLOAD`）：


> **本模板与圣域的关键差异**（这是它合规的原因）：
> 1. **不注入 `possibleBiomes()`** → 不碰 R3；
> 2. **不注入 `getNoiseBiome()`** → 不碰 `S1-城墙本体.md:1523` 的整体拒绝；
> 3. **维度隔离用硬比较 `dimension() != Level.OVERWORLD`**（`:45-46`），**不用实例身份白名单** → 免疫包装器错位（§2.3）；
> 4. **sampler 只做"这盘 RandomState 是不是长城的"锚**，通过 `IdentityHashMap` + `==`，不依赖任何第三方类的身份。

### 7.3 ⚠️ 本模板的**已知代价**（必须让用户知情）

采用路径 C 会**放弃 `possibleBiomes()` 注入**，由此产生一个**功能性缺口**：

【javap】`ChunkGenerator.applyBiomeDecoration` 偏移 `163-177` 会对从区块 sections 收集到的群系集合执行 `retainAll(possibleBiomes())`。如果长城群系**不在** `possibleBiomes()` 里，那么：
- ✅ 区块的 **biome 本身**会被正确写成长城群系（写入在 HEAD，`retainAll` 只作用于局部 Set）；
- ❌ 但**长城群系 `features[9]` 里的矮树/草/花不会在那个区块被放置**（该群系在 `retainAll` 后被剔出待处理集合）。

**这意味着"只抄路径 C"可能得到"群系正确但植被不长"的结果。**

**三条出路（需要用户裁定）**：

| 出路 | 做法 | 合规性 | 代价 |
|---|---|---|---|
| **出路 1：不依赖 features，全部自己写** | 长城本来就有 `generation/ProductionWallPipeline` 等自建写入路径；矮树由长城自己的代码放，不靠群系 features | ✅ 完全合规 | 需要自己实现树木放置；但长城已有 `ProtectionSnapshot`/`VegetationGuard` 等基础设施 |
| **出路 2：只注入 `getNoiseBiome`（路径 B）** | 追加 `@Mixin(MultiNoiseBiomeSource.class)` | ⚠️ R3 字面不禁，但 `S1-城墙本体.md:1523` 整体拒绝 → **需用户显式授权** | 有包装器时可能失效（§1.6） |
| **出路 3：申请 R3 例外** | 复刻 `BiomeSourceMixin` | ❌ 直接违反 R3 + 规格书明文点名拒绝 | **不建议** |

> **本报告不替用户选路**，但明确给出技术判断：**出路 1 是唯一"既合规又确定可用"的路径**，而且它恰好与长城的整体架构（自建 `ChunkWallWriter`、`ProductionWallPipeline`）一致——长城**本来就不靠生物群系 features 来建造城墙**。

## 8. 陷阱清单

> 分级：【实战坑】= 会导致功能失效或崩档；【隐患】= 特定条件下才出问题；【规范坑】= 与长城规则冲突。

### T1 【实战坑】`possibleBiomes()` 是 memoize 的，注册时机可能已经太晚

**第一步：`possibleBiomes()` 是永久缓存。**
【javap】`BiomeSource.<init>` 把 `possibleBiomes` 包成 `Suppliers.memoize`（偏移 `4-14`）：
```
protected BiomeSource();
   4: aload_0
   5: aload_0
   6: invokedynamic #51   // get:(BiomeSource)Supplier   ← 指向 collectPossibleBiomes
  11: invokestatic  #57   // com/google/common/base/Suppliers.memoize
  14: putfield      #59   // Field possibleBiomes
```
⇒ **首次 `.get()` 之后，该实例的 `possibleBiomes` 内容永久固定**，后续任何 `addAll` 都只影响"新造一个集合"的返回值语义，**如果调用方拿的是缓存**。

**第二步：首次求值发生在 `ServerLevel` 构造期（早于 `LOAD`）。**
求值链路（逐跳均有 javap 偏移）：

| 跳 | 位置 | 关键偏移 |
|---|---|---|
| 1 | `MinecraftServer.createLevels` `new ServerLevel(...)` | `118-145` |
| 2 | `MinecraftServer.createLevels` `Map.put(levels, OVERWORLD, level)` | `150-159` |
| 3 | `ServerLevel.<init>` `new ServerChunkCache(...)` | `274-279` |
| 4 | `ServerChunkCache.<init>` `new ChunkMap(...)` | `109` |
| 5 | **`ChunkMap.<init>` `ChunkGenerator.createState(...)`**（**在构造器内**：下一个方法声明在偏移 `327`） | **`290`** |
| 6 | `ChunkGenerator.createState` → `ChunkGeneratorStructureState.createForNormal` | — |
| 7 | **`createForNormal` 的 `Stream.filter` 谓词就是 `hasBiomesForStructureSet`** | `7-13` `invokedynamic #105 // test:(BiomeSource)` |
| 8 | **`hasBiomesForStructureSet` 无条件调 `possibleBiomes()`** | **`22`** `invokevirtual #149` |
| 9 | `ChunkGeneratorStructureState.generatePositions` 也调 | `4` |

`hasBiomesForStructureSet` 的调用是**无条件**的（偏移 `22` 在 `anyMatch`（`35`）之前），主世界必有 structure set → **第 5 步一执行，`possibleBiomes()` 就被求值并缓存**。

**第三步：Fabric 的 `LOAD` 在 `Map.put` 之后才派发。**
【源码】`fabric-lifecycle-events-v1` 的 `MinecraftServerMixin.java:75-81`：
```java
@WrapOperation(method = "createWorlds",
        at = @At(value = "INVOKE", target = "Ljava/util/Map;put(Ljava/lang/Object;Ljava/lang/Object;)Ljava/lang/Object;"))
private <K, V> V onLoadWorld(Map<K, V> worlds, K registryKey, V serverWorld, Operation<V> original) {
    final V result = original.call(worlds, registryKey, serverWorld);   // ← 先 put（第 2 步）
    ServerWorldEvents.LOAD.invoker().onWorldLoad(...);                  // ← 再派发
    return result;
}
```

**【推导，未运行验证】** ⇒ 综合三步：**当 `LOAD` 回调执行时，主世界的 `possibleBiomes()` 早已被求值并缓存**。此时 `BiomeSourceMixin` 的 `addAll`（`:49-51`）要么作用于**已被缓存的旧集合**（若上层持有的正是缓存对象），要么其新返回值再也无人读取——**两种情况都对世界生成不产生任何影响**。

**若该推导成立，则圣域 `BiomeSourceMixin` 是死代码。**

**⚠️ 本条推导的两个不确定性（诚实标注）**：
- **不确定性 A**：`Suppliers.memoize` 缓存的是**整个 `Set` 对象**。若 `MultiNoiseBiomeSource.collectPossibleBiomes()` 每次都返回新 `ImmutableSet`，那么 `possibleBiomes()` 返回的是**第一次那份不可变集合**。注入方 `callback.getReturnValue()` 拿到的是它 → 新建 `LinkedHashSet` → `Set.copyOf` 新集合 → **`setReturnValue` 只影响本次调用的返回值**。所以只有当**调用方在每次需要时都重新调 `possibleBiomes()`** 时注入才可能生效。`applyBiomeDecoration` 偏移 `169` 确实是每次调用都重新调 —— **因此注入对它是可能生效的**，前提是注入发生在它之前。本报告 T1 的落点是：**注入发生在 `LOAD`（已晚于首次求值），但对 `applyBiomeDecoration` 而言"晚"不等于"无效"**——因为 `applyBiomeDecoration` 在区块生成时才跑，远晚于 `LOAD`。
- **更正**：因此 T1 的**严格表述**不是"注入必然失效"，而是：**注入对"在 `LOAD` 之前就已求值并消费过 `possibleBiomes()` 的路径"无效**（如 `ChunkGeneratorStructureState.generatePositions` 的结构放置判定、以及 `ChunkGenerator` 构造器里的 `featuresPerStep` memoize），**对"每次调用都重新取"的路径（`applyBiomeDecoration` 的 `retainAll`）仍可能生效**。

**真正需要警惕的是 `featuresPerStep`**：【javap】它由 `ChunkGenerator.<init>` 偏移 `14-25` 建为 `Suppliers.memoize(...)`，body（`lambda$new$2`）是 `List.copyOf(possibleBiomes())` → `FeatureSorter.buildFeaturesPerStep`。而 `ChunkGenerator` 实例来自数据包加载（早于 `ServerLevel` 构造，更早于 `LOAD`）。**若 `featuresPerStep` 在 `LOAD` 之前被求值，则长城/圣域群系的 `PlacedFeature` 永远不在 feature 表里** —— 这将使 §7.3 的功能性缺口**无法通过任何注入时机规避**。

**给长城的行动项（三条，都是必须实测的）**：
1. 用一次断点/日志确认 `possibleBiomes()` 与 `featuresPerStep` 的**首次求值时刻**各自落在 `LOAD` 之前还是之后；
2. **不要以"圣域也这么干"为由解禁 R3** —— 本条推导若成立，圣域的做法本身就没有生效；
3. 若确认 `featuresPerStep` 早于 `LOAD`，则 §7.3 的**出路 1（长城自己写植被）是唯一可靠路径**，出路 2/3 都应放弃。

### T2 【实战坑】`instanceof MultiNoiseBiomeSource` 门禁在包装器下会失败

【javap】Lithostitched `InjectorBiomeSource extends net.minecraft.class_1966`（= `BiomeSource`），**不是 `MultiNoiseBiomeSource`**。
【javap】`BiomeInjectorManager.applyBiomeInjectors` 偏移 `441-474` 用 `new InjectorBiomeSource(oldSource)` + `ChunkGeneratorAccessor.setBiomeSource(...)` **替换**掉 ChunkGenerator 的 biomeSource。
【源码】`GoldenErdtreeSanctuaryMod.java:92-93` 登记的正是 `getBiomeSource()`（即外层包装器）；而 `BiomeSourceMixin.java:44` 要求 `this instanceof MultiNoiseBiomeSource`。
**【推导】** 外层不满足类型门禁、内层不满足身份白名单 → **两处 BiomeSource 注入同时失效**。

**给长城的行动项**：若走路径 B（`getNoiseBiome` 注入），**不要把门禁写成实例身份白名单**。正确做法见 §7.2(d)：**用 `Level.dimension() == Level.OVERWORLD` 硬比较**做维度门禁，用 `Sampler` 做上下文查找——两者都不依赖第三方类的身份。

### T3 【实战坑】`quartLocal` 不能用 `%` 代替

【javap】`QuartPos.quartLocal(v) = v & 3`。对负坐标：`-1 & 3 = 3`（正确）；`-1 % 4 = -1`（**错误 → 数组下标 -1 → `ArrayIndexOutOfBoundsException`**）。

圣域 `SanctuaryBiomeWriter.java:44, 50-52` 全部用 `QuartPos.quartLocal`。**抄的时候不要"优化"成取模。** 世界坐标在负半轴极其常见（长城选址可能在任何象限）。

### T4 【实战坑】`fillBiomesFromNoise` 的回调收到的是**绝对** quart 坐标

【javap】`LevelChunkSection.fillBiomesFromNoise` 偏移 `50-63`：`iload_3; iload 8; iadd` —— 传入 `quartX + localX`，**不是** `localX`。
**但** `PalettedContainerRO.get(...)` 要的是**局部** 0..3 下标。
圣域用 `QuartPos.quartLocal(sampleQuartX)` 把绝对坐标还原成局部（`:50-52`）。**若直接把回调参数丢给 `original.get(...)`，会越界或取错格子。**

### T5 【实战坑】`LevelChunkSection` 没有 biome setter，只能走 `fillBiomesFromNoise`

【javap】`LevelChunkSection` public 方法全表（§3.2）中无任何 biome 写方法；`biomes` 字段是 private；`PalettedContainerRO` 只有 `recreate()` 返回**可变副本**但**无处放回**。
**结论**：`fillBiomesFromNoise(resolver, sampler, qx, qy, qz)` 是唯一写入口。不要试图反射改 `biomes` 字段（会被 `PalettedContainer.acquire/release` 的锁语义与 palette 位宽维护弄坏）。

### T6 【隐患】`sections[]` 数组元素可能为 null

【javap】`ChunkAccess.<init>` 偏移 `60-70` 只 `anewarray`（长度 = `getSectionsCount()`），**元素初值 null**；偏移 `110-123` 之后才由 `replaceMissingSections`（偏移 `175`）把 null 填成 `new LevelChunkSection(registry)`。
【javap】`ChunkAccess.getSection(i)` = `getSections()[i]`，**不做 null 检查**。

圣域 `SanctuaryBiomeWriter.java:37-39` 直接 `sections[sectionIndex].getBiomes()`，**没有 null 检查**。
**判断**：在 `applyBiomeDecoration` / `CHUNK_LOAD` 时机，区块已过 `replaceMissingSections`，**实践中安全**；但如果长城要在更早的时机（例如 `fillFromNoise`）复用它，**必须自己加 null 检查**。

### T7 【隐患】`apply()` 的早退判据范围与地形不一致

圣域 `SanctuaryBiomeWriter.java:20` 用 `context.layout().intersectsChunk(...)`（**只判主圆**），而地形用 `context.intersectsTerrainChunk(...)`（**圆 ∪ 外部水系**，`SanctuaryRuntime.java:126-129`）。
**后果**：外部水系影响的地形会被整形，但**那些地方的群系不变**（仍是原版群系）。
**给长城**：明确自己的口径——长城走廊若有"缓冲带/引道"，群系要不要跟着走？必须显式决定，不能默认套用。

### T8 【隐患】`CHUNK_LOAD` 兜底写的开销

`GoldenErdtreeSanctuaryMod.java:121-125` 对**每个**主世界区块加载都调 `apply`。虽然 `apply` 在 `intersectsChunk` 早退（`:20-22`），但早退前仍有 `SanctuaryRuntime.get(sampler)`（通常被 `lastLookup` 命中，成本可忽略）。
**给长城**：长城有 40ms 性能门槛（`docs/S1-S5实施规格/README.md:29`），若加这条兜底，**必须计入分配与耗时证据**，不能默认"早退就是免费"。

### T9 【规范坑】`possibleBiomes` 与长城 R3 直接冲突

见 §6.2。**额外提醒**：`docs/全工程红队审查-20261006.md:209` 记录长城连"注释里出现该 API 名"都列为合规清理项。因此**若要在长城文档里讨论圣域这条实现，措辞需谨慎**——本报告已在正文中使用该标识符（属于查证文本，非生产源码）。

### T10 【规范坑】新增 `worldgen/*.json` 会改世界指纹 → 旧档拒绝

【源码】`lifecycle/GenerationResourceFingerprint.java:43-50` 遍历 `worldgen` 前缀资源；`lifecycle/WorldRecipeGuard.java:60-63` 在不匹配时抛 `WORLD_RECIPE_MISMATCH: generation resources changed; create a new world`。
**这是设计使然**，但**必须提前告知玩家"要开新世界"**。

### T11 【规范坑】新群系默认材质为 `STONE`

【源码】`decay/BiomePaletteIndex.java:82-91` 判定顺序 `RED_SANDSTONE → SANDSTONE → DEEPSLATE → 兜底 STONE`。新群系**不进任何 palette tag 就静默变 STONE**。
【源码】`BiomePaletteIndex.java:65-70`：红砂岩族必须是砂岩族**子集**，否则抛 `INVALID_RESOURCE`。

### T12 【实战坑】`TreeFeatureMixin` 会连长城自己的树一起抑制

【源码】`mixin/TreeFeatureMixin.java:17-32` 对 `TreeFeature.class` 做 HEAD 注入，**不区分命名空间** → 长城自己的矮树（只要用 `minecraft:tree` 类型）**同样会被取消**。
**给长城**：这是**已知且有意**的设计（走廊内不留树）。如果期望"长城群系的矮树能长在墙边"，必须**先改 `VegetationGuard` 的走廊范围**，否则白做。

### T13 【实战坑】`possibleBiomes` 失效后自家 features 也不生效

见 §7.3。**这是本报告对长城最重要的一条**：它决定了"只抄路径 C"是否足够。**必须实机二分**（§1.6 给出了测试方法）。

## 10. 一句话结论

圣域的群系注入是**三层**：`possibleBiomes` 注入（**违反长城 R3**）、`getNoiseBiome` 注入（形式不违反 R3，但规格书整体拒绝）、以及**真正扛事的第三层——`SanctuaryBiomeWriter` 在 `applyBiomeDecoration` HEAD 用 `fillBiomesFromNoise` 物理重写区块的 4×4×4 quart 群系调色板**。

本次相对既有取证的三点增量：
1. **【javap 硬证据】`possibleBiomes()` 的首次求值发生在 `ServerLevel` 构造期（`ChunkMap` 偏移 `290` → `createState` → `hasBiomesForStructureSet`），必然早于 `ServerWorldEvents.LOAD`**；而圣域正是在 `LOAD` 里才注册。这对依赖 `possibleBiomes` 的判定路径构成时机缺陷。
2. **【javap 硬证据】Lithostitched 的 `InjectorBiomeSource` 包装发生在 `DedicatedServer.initServer`（早于 `loadLevel → createLevels → LOAD`）**；由于 `BiomeSourceMixin:44` 要求 `instanceof MultiNoiseBiomeSource`、且两处注入都要求 `isOverworldSource(实例)`，**在包装场景下两处 BiomeSource 注入双双不成立**——真正把群系落到世界上的只有 `SanctuaryBiomeWriter`。
3. **【源码】圣域"不放树"是纯数据行为**（`features[9]` 留空），**没有任何代码拦截树**（全量 grep `TreeFeature` 零命中）；唯一涉及原木/树叶的代码是 `SanctuaryTerrainFinalizer.java:367` 的河道清理覆盖面，不是通用防树。

**给长城的落地判断**：可照搬的是**路径 C（`SanctuaryBiomeWriter` 式区块调色板重写）+ `SanctuaryRuntime` 的 volatile 快照线程模型 + `applyBiomeDecoration` HEAD 注入点**（§7.2 模板），并**改用 `Level.dimension()` 硬比较做维度门禁**以免疫包装器；**不可照搬**的是 `BiomeSourceMixin`（R3）与 `OVERWORLD_SOURCES` 实例身份白名单（包装器下必然错位）。代价是 `retainAll` 会让长城群系自己的 `features[9]` 不派发（§7.3，与 `_查证-群系时序与注入点-20261006.md` §7.2 结论一致）——因此**矮树应由长城自己的写入路径承担，而不是挂在群系 features 上**，这与长城既有架构（`ProductionWallPipeline` / `ChunkWallWriter` / `TreeFeatureMixin`）天然吻合。**§1.6 的二分实验与 §T1 的 `featuresPerStep` 求值时刻是本方案落地前必须实测的两项前置。**
