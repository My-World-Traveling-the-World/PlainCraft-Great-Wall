## 3. Q2：最终路线 mask、快速查询与生命周期

### 3.1 几何真值

使用 `PlanWindow → SegmentPlan.stations/sites`，不是 `axis + AnchorField`。已有 [VegetationGuard.java:20](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/generation/VegetationGuard.java:20) 使用最终 stations/sites；[WallTypes.java:342](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/model/WallTypes.java:342) 定义 SegmentPlan，:360 定义不可变 PlanWindow。

把 [VegetationGuard.java:14](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/generation/VegetationGuard.java:14) 的盒构建提取成共享纯 helper `corridorBoxes(PlanWindow)`，让旧 guard 与新 mask 读取**同一份不可变盒列表**。重构不得改变一格边界、站点跳过规则或原保护结果；先做逐盒一致性红例。

定义：

- **H**：现有硬保护盒的 XZ 并集。普通段 ±44，潜在出口 ±68，非 suppressed site 外扩 32；依据同文件 :33、:37、:43。
- **B**：H 向 XZ 每侧外扩 64 后的并集，即专属群系景观域。
- **LOW origin 带**：到 H 的 L∞ 离散距离 `8 ≤ d < 32`。
- **EDGE origin 带**：`32 ≤ d < 64`。

`8/32/64` 是本方案新增的明确初值，不冒充旧规格冻结值。进入 biomePolicy hash；调数值会换 recipe。H 仍是原保护域，不从中心线重新计算一个更窄的圈。特别注意：现有每段同时加入 ±44 与 ±68，后者可包住前者；不能声称某个普通路段只需离轴 45 格就能种树。

离散距离对半开矩形 `[minX,maxX)×[minZ,maxZ)`：

```text
dx = max(minX - x, 0, x - (maxX - 1))
dz = max(minZ - z, 0, z - (maxZ - 1))
dH(x,z) = min_over_boxes(max(dx,dz))
```

运算先提升 long，扩盒用 exact/边界检查；不得在负坐标使用截零取整。

V1 **保留当前 guard 对已规划断口的保护政策**，不另行在 breaks 上删盒。因此“沿路线”指最终已规划走廊，包括其已规划断口保护，不是“只对已经写出砖的格子换群系”。不补出终止之后的站点/轴延长线；永久海洋终止沿用当前 prefix/window 的过滤，[PlannerScheduler.java:205](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/planning/PlannerScheduler.java:205)。

完整 tree footprint 在 B 内的测试必须检查整个有限 box 覆盖，不能只测四角：并集可能有洞。原版小半径可直接按位图逐列检查。

## 4. Q3：最小 owner writer，以及 B2 的重新判定

### 4.1 B2 在新裁决下不再要求大型阶段图改造

**不增加 CARVERS→SURFACE 依赖，不改邻块，不做本底装饰 view。**

理由：

1. J6 证明 owner FEATURES 要求 3×3 邻块 CARVERS，因此其 SURFACE 已完成。owner HEAD paint 不会倒回修改这些已完成的地表输入。
2. J5 的邻 FEATURES 可看见邻块已 paint 或未 paint 的身份，装饰可随顺序变化；用户已接受这部分变化。
3. H 内禁树依赖锁外 guard snapshot，不依赖邻 biome 已 paint，也不依赖专属 biome 的空 features。因此邻身份差异不应造成硬圈漏树。
4. C1/C2 支持正常 C2ME 路径采用同类原阶段依赖和原锁；整包变换类、非正常 fallback 仍需认证。

这里撤掉的是“邻装饰身份必须完全一致”的设计要求，不是关闭线程安全审查。**Vanilla/C2ME owner 的写权、别的 mod 改容器的顺序以及地表对照仍是进入正式接线的验证前置。**

### 4.2 最小写法

挂在 `ChunkGenerator.applyBiomeDecoration` HEAD，传入原生已拥有的 ChunkAccess：

- 显式 OVERWORLD 与当前授权 session 检查。
- 从 owner-ready snapshot 取 16 个 quart 列。
- 只改本 chunk，public `fillBiomesFromNoise` 自行替换 biomes 字段；**不需要自行 putfield、反射、access widener 或 biomes 字段 accessor Mixin**，依据 J7。
- 保留未命中 XZ/Y 的旧值，修改后 `chunk.setUnsaved(true)`。
- 不取邻 chunk，不做 CPU 地形采样，不追加等待。

选择 **thinY**：owner 在 native decoration 前，从已有 WORLD_SURFACE_WG map 的每 quart 中心列取最高占用格 H，paint block 区间 `[H-8,H+32)`。Y 政策也入 hash。未支持该 heightmap 合同的 generator 明确拒绝该 profile，不偷偷改成全 Y。

骨架，helper 为拟新增内部契约，**NOT_COMPILED**：

```java
void paintOwner(ChunkAccess chunk, Climate.Sampler sampler,
                ReadyBiomeSnapshot ready) {
    ready.assertOwnerAndEpoch(chunk.getPos());
    var heightmap = requireExistingSurfaceWg(chunk);
    var columns = freezeQuartColumns(chunk, heightmap, ready.mask());
    boolean changed = false;
    for (int i = 0; i < chunk.getSections().length; i++) {
        int qy = QuartPos.fromSection(chunk.getMinSection() + i);
        if (!touches(columns, qy, qy + 4)) continue;
        var section = chunk.getSections()[i];
        var old = section.getBiomes();
        section.fillBiomesFromNoise((x, y, z, ignored) -> {
            int n = QuartPos.quartLocal(x) + 4 * QuartPos.quartLocal(z);
            var c = columns.get(n);
            return c.target() != null && c.minQuartY() <= y && y < c.maxQuartYExclusive()
                ? c.target()
                : old.get(QuartPos.quartLocal(x), QuartPos.quartLocal(y),
                          QuartPos.quartLocal(z));
        }, sampler, QuartPos.fromBlock(chunk.getPos().getMinBlockX()), qy,
           QuartPos.fromBlock(chunk.getPos().getMinBlockZ()));
        changed = true;
    }
    if (changed) chunk.setUnsaved(true);
}
```

`freezeQuartColumns` 的具体规则：

1. 16 个采样点为 owner-local `(4*qx+2,4*qz+2)`；使用已有 `Heightmap.getHighestTaken`。
2. block 区间裁到 `[minBuildHeight,maxBuildHeight)`。
3. 非空区间 `[lo,hi)` 转为 `[QuartPos.fromBlock(lo), QuartPos.fromBlock(hi-1)+1)`，不能把 hi 当包含端点。
4. 返回 `List.copyOf` 的 immutable column records；同一 native producer 的重复调用复用首次 frozen columns，不随后来植被高度重新算带。
5. `requireExistingSurfaceWg` 不调用可能隐式 prime 的 `getHeight`，依据 J11/J12；缺失为 adapter 合同错误。`hasPrimedHeightmap` 仅“存在”不等于内容已正确填充。

thinY 减少深洞穴群系改变，**不保证所有洞穴不变**；浅洞、峭壁与 quart 量化仍可能变化。高度图也会包括水面，海岸/水面单列用例；V1 不在水下放景观树。没有本底持久 store：未命中值留在原生容器，命中身份随 chunk 正常保存；退出重进与中途异常仍要测。

新增一个 `ChunkGeneratorBiomeMixin` 同时承担 HEAD paint 与 Q4 TAIL dispatch；必须确认 `require=1` 的本版 descriptor，在生产 intermediary 变换后导出验证，不靠 MCP 字符串反射。

### 5.3 Modifier 与 TAIL 骨架

modifier 使用 `MapCodec`，不是 `Codec`，依据 J10。band/profile 验证应在 freeze 阶段完成，未知值拒绝，不当 edge 或 fallback。

```java
public final class RouteBandPlacementModifier extends PlacementModifier {
    static final MapCodec<RouteBandPlacementModifier> CODEC =
        RecordCodecBuilder.mapCodec(i -> i.group(
            Codec.STRING.fieldOf("band").forGetter(v -> v.band),
            ResourceLocation.CODEC.fieldOf("profile").forGetter(v -> v.profile)
        ).apply(i, RouteBandPlacementModifier::new));

    @Override
    public Stream<BlockPos> getPositions(
            PlacementContext c, RandomSource random, BlockPos pos) {

        if (!Level.OVERWORLD.equals(r.getLevel().dimension())) return Stream.empty();

        var bounds = snapshot.certifiedProfile(profile).completeBounds(pos);
        return snapshot.allows(r.getCenter(), pos, band, bounds)
            ? Stream.of(pos) : Stream.empty();
    }

    @Override
    public PlacementModifierType<?> type() { return ROUTE_BAND_TYPE; }

```

```java

    for (var entry : ready.landscapeFeaturesInStableIdOrder()) {
```

`claimLandscapeAttempt` 的可变阶段标记放 FeatureSlot 的 CHM，不放 immutable mask；key 带 native attempt 身份，生命周期随真实 producer。只允许同一次 action 从 NOT_STARTED→STARTED 一次，重复 TAIL 不再派发。成功结束记 DONE；异常记 FAILED 并传播，不把部分树写入后再重试当幂等成功。升级/已完成 FEATURES 路径不重做；新会话重进也不能给已完成的 chunk 再装饰一遍。

## 8. Q7：beforeRoad / afterRoad 的明确启动链

### 8.1 最小状态机与成功含义

新增 WallStartupCoordinator，状态仅不可变快照，由 CHM 承载。阶段是：

```text
CREATED → BEFORE_ROAD → BEFORE_READY
    → ROAD_TERMINAL(SUCCESS 或合法 SKIPPED)
    → AFTER_ROAD_BULK → BULK_READY → GAME_LOW
任意阶段 → FAILED / STOPPING → DRAINED
```

`beforeRoadReady` 必须包含：

1. frozen source/资源/biome profile 和 registry epoch 完成，root 仍单 lane。
2. recipe 持久化后安装 planner/barrier 成功。
3. 安装即启动 **demand-only pump**，不自动提交原 0..3 bulk。
4. history 恢复、S3 服务与 Road adapter、session/height/provider 绑定完成。
5. 启动按需计划不依赖正常 tick，不等待道路终态。

当前证据：[ProductionSession.java:96](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/lifecycle/ProductionSession.java:96) 的安装依赖 server.execute；:112 调旧 startupPump；:120 history 异步；:154 装 adapter；:161 installed.complete；:173 recipeReady 只等 installed。**installed 不等于 gameplay/history/SPI 都 ready。**

最小增量：增加独立 `gameplayReady` promise，只有 :157 附近全部 assembly 成功才完成；fail/close 同时异常完成。不要从 :160 的 `exceptionally(...return null)` 推出成功。beforeRoad 聚合 installed + gameplayReady + demand pump started。

`beforeRoad` 不等 provider 的 `whenReady` 或端点 ensureConnection 副作用；[PlanningInteropRegistry.java:13](D:/云游四海-Mod源码/roadweaver/common/src/main/java/net/shiroha233/roadweaver/api/interop/PlanningInteropRegistry.java:13) 区分这个副作用信号与初始外部规划。

### 8.3 纯 DTO soft bridge

新增 Road common `api/interop/WallStartupRegistry.java`：纯 JDK record/enum/future/Hook/CHM。新增墙 `compat/road/RoadStartupBridge.java`，仅在 Loader 检测 Road 后加载。

```java
    CompletionStage<Void> afterRoad(Run run, Terminal terminal);
```

world path+dimension 用于注册定位，真正调用还校验 runtime UUID/epoch；seed 不能标识 session。每边在自己的 Mojmap 编译边界用 level 取得路径，跨 jar 不传原版对象、也不反射原版名字。

### 8.4 成功、失败、跳过和 owner 等待

Road 当前 [InitialGenManager.java:945](D:/云游四海-Mod源码/roadweaver/common/src/main/java/net/shiroha233/roadweaver/generation/InitialGenManager.java:945) 捕获失败后调用 abort 并正常返回；:2016 清 active。**RETURN 或 active=false 都不是 success 证据。**

新增 outcome：

- SUCCESS 仅在 flushAndFinish 收尾成功后发布；:1975 durable completion 是关键锚点。
- 合法 SKIPPED 给明确原因：NO_ROAD、已有完成 checkpoint、配置明确禁用、真实无需任务等。无法解释的 active 残留、silent begin 早退不能当成功。
- abort :2007 发布 FAILED，停止发布 CANCELLED。
- 返回但无 terminal 是协议错误；不启动 bulk、不放行游戏。
- 所有 promise 属于 run，旧 session 晚回调不能完成新 run。

`awaitOnServerOwner` 只允许 prepareLevels 的 server owner、锁外。用 managedBlock 继续泵 server executor，结束后从已完成结果传播失败；不能裸阻塞安装所需的 server.execute。依据现有 Road :1079 的 owner-pump 等待模式；**不把其中 join/get 复制到新增 worldgen 链**。

coordinator 骨架：

```java
CompletableFuture<ReadyStamp> once(Stage key,
        Supplier<CompletionStage<ReadyStamp>> action) {
    var producer = new CompletableFuture<ReadyStamp>();
    var existing = promises.putIfAbsent(key, producer);
    if (existing == null) server.execute(() -> startOrFail(key, producer, action));
    return (existing == null ? producer : existing).copy();
}
```

startOrFail 检查 run/epoch，捕获同步与异步异常，completion 回 owner；CHM compute 不跑 freeze/外部 callback/完成 promise。stop 先拒绝并完成未决阶段，再真实 drain。

## 9. Q8：N-lane 最小实现，root 不动

### 9.1 范围

**只扩独立 route jobs；root 保持同一个首 lane。** [WorldBootstrap.java:207](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/lifecycle/WorldBootstrap.java:207) 当前建两 handle，:218 RootSearch 用 first；[OracleLane.java:36](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/terrain/OracleLane.java:36) 限制 0..1。

RootSearch.java 不改。bootstrap 建 N 个惰性 handle，root 仅启动 0；transfer 原 handle，不重新造 root oracle。route 的 independently ready jobs 才允许分配更多 lane。

### 9.2 N 策略

```text
N_active = min(CPU_cap, memory_cap, J_ready)
CPU_cap  = max(1, availableProcessors - reserve)
reserve  = 初始 2 个逻辑线程，作为执行政策而非几何配置
```

16 逻辑线程机器 CPU 上限可先为 14，**不是认证了 N=14**。初始验证 1/2/4/8，标定后才开放更高档。J_ready 只计依赖已满足的 single-flight 任务，不计调用者个数或未 ready future；最多 N 个目标闭包内 route 的有限 lookahead，不能靠扩大世界范围凑满 CPU。

不改 maxGeometryInflight=4、parent plan/geometry admissions 各 4、IO128、缓存/lease 预算。锚点：[PlannerScheduler.java:318](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/planning/PlannerScheduler.java:318)、:509、:510。四个连续 geometry 去重邻 route 通常只有约六个 route 候选；root、prefix 与小任务窗不保证全核饱和。

“用满硬件”解释为：**启动阶段在认证内存与独立任务额度内尽量使用 CPU**，不是承诺 GPU 自动参与，也不是 N 倍加速。

### 9.3 惰性初始化与内存证书

当前 [PlannerScheduler.java:397](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/planning/PlannerScheduler.java:397) 在确认 pending job 前启动 lane。扩 N 时必须先确认有 job，再申请初始化/驻留许可，避免空闲时造 N 份 oracle。

初始初始化并发限 2；新增 OracleLane `initializationSettled`，只有 native 构造真实结束、初始化 TL 已撤销才完成。现有 [OracleLane.java:148](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/terrain/OracleLane.java:148) 的 close 可提前让公开 ready 失败，不能据此归还 native 构造峰值额度。

内存测量方法，全部 NOT_RUN：

1. 固定同输入、相同 adapter/profile，记录 shared baseline heap/native/thread-stack。
2. 对单 lane 初始化→代表性 cursor→steady→close/drain→GC 测 Rsteady 与初始化额外峰值 Dpeak，覆盖最重地形/cursor/maps。
3. N=1/2/4/8 阶梯测同时初始化与最长 job，不能仅把账面 cache 64/256/256 MiB 相加当 oracle 实测。
4. 以保守上界准入：

```text
M_peak = shared
       + N_resident * Rsteady
       + initializing_count * Dpeak
       + jobs/masks/leases/IO reservations
       + safety_headroom
```

初始化瞬态许可在 settled 后归还，驻留许可在真实 owner close/drain 后归还。旧公开 future 失败不释放尚在构造的占用。未标定时保持已认证档，不能写“每 lane X MiB”虚构数字。

### 9.4 游戏低档与退休

- BULK_READY 后停止高档新领取，允许已有 owner-local batch 收尾；活动 cursor 不迁 lane。
- 游戏保留至多两 owner，总采样并发初始设 1，后台最多一个 lease；内存只容一 lane 时关闭主动 background。
- 多余 slot 停止领取新 job，原 cursor 由原 owner 完成/显式取消收尾，清引用后 close/drain。退休 lane 不再 dispatch。
- 退档期间在飞行旧 batch 计入总并发，不能一边“退档”一边另起游戏任务超额。
- 若需求要插队，只在 batch 边界由同 owner 暂存/恢复自己的 cursor；不把 cursor 传给另一线程。否则如实报告需求等当前批次的延迟。
- 延续原 credits/deadline 和优先级，先需求后后台；25ms 是切片目标，单个 primitive 不能被强行抢占。40ms 记录/当前已授权门禁政策不由本提案擅改，不用提高 timeout 出性能证书。

## 13. 与道路门洞/尽头路兼容，以及对上一轮判断的修正
