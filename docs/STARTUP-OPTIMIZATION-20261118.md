# 长城预热与游戏内补建优化审查

## 1. 结论和用户要求

开局仍有明确优化空间，先处理精采样缓存所有权、负数二分、地基坐标表和重复编译，再考虑并行度。保留启动规划/结构绕行/精采样/编译/发布避让足迹、游戏内加载区块施工的分工。用户最新要求：首次施工直接落实已发布计划，漏检建筑也覆盖，不再因世界现状不同跳过。已完成同版本计划的持久标记仍应保护玩家后续编辑，不能重开反复强刷。

有限长城按总长、无限另设预热范围尚未实施。当前有限≤10万格全量，超长或无限仅前4段；不能把扩大规划误实现成启动同步加载全部施工区块。正式模板接线等待用户素材。

## 3. 源码核实的改进点

### GW-01：缓存没有跨通道共享且静态持有未释放（P1）

NoiseSurfaceSampler.java:103–105声明SHARED，:132用identityHashCode(randomState)加海平面/高度作键；CpuTerrainOracle.java:205每个oracle新建RandomState；PlannerScheduler.java:297–303经OracleLane工厂建立多个oracle。同一冻结地形因此通常分表，和“所有lane共享”注释相反。identityHashCode也不是不会碰撞的世界身份。

CpuTerrainOracle.java:415–422关闭只清状态与active；全量搜索SHARED只有声明/computeIfAbsent，无移除。容量限额作用于各表，不能当作所有lane的总预算；实际堆占用未测。

提取原键表达式，以16个不同状态对象模拟lane，得到16张表，第二lane读不到第一lane的同键值；丢弃lane引用后静态表仍16项。这是键/持有关系实验，不是完整NoiseChunk并发测试。

修法：冻结输入/会话显式拥有一份有界结果缓存并注入lane，仅共享不可变高度、水面及支撑结果；RandomState/NoiseChunk仍归单lane。关闭时停止认领、处理在途、释放缓存；同单元并发只算一次，失败/取消必须唤醒等待者。不可简单扩大现有静态表。

### GW-02：地表二分对负数使用无符号中点（P1；道路也存在）

NoiseSurfaceSampler.java:400–414，lo=minY-1，:409用(lo+hi)>>>1；和为负时得到超出区间的巨大正坐标。提取原方法，用单调密度替身遍历-64..319共384阈值：95项错，阈值-40/0/20均返回-65。探针改成lo+((hi-lo)>>>1)后0错。

长城:315–319丢弃触底估计并从世界顶下降，因此会增加下降工作；未测多走多少格，也未证明最终高度必错。道路common/.../NoiseChunkHeightSampler.java:207有相同表达式，而:119–124只是把起始单元夹到下界，需优先补真实采样对照。

两仓分别修中点、补负高度/边界/全高全低密度和真实下降对照；先核有效高度下差值不溢出。算术正确不等于任意模组密度单调，不应顺便改变道路触底政策。

### GW-03：packed-XZ地基表触发JDK不可变表聚集（P1性能风险）

PlanningChunkCompiler.java:43–51建Long→Integer地基表并Map.copyOf；RealizationPlanner.Input:36再Map.copyOf。packed-XZ的Long.hashCode近似x xor z，规则坐标大量聚集，JDK21 MapN开放寻址建表/查询会退化。

Map.copyOf遇到已有不可变表通常直接返回，不能说每cell都复制完整表。其他列缓存已有私有HashMap快照，不能当缺失重提。

独立JDK21合成矩形坐标，3轮预热/7轮测量，512MiB JVM，构建中位数：

| 条数 | Map.copyOf | 私有HashMap快照+只读包装 |
|---:|---:|---:|
| 4,096 | 16.985ms | 0.711ms |
| 16,384 | 519.375ms | 1.594ms |
| 32,768 | 2,199.388ms | 2.843ms |

这不是实际地基分布，不外推启动倍数。先记录真实条数/分布/建表查询耗时，再统一生产者和Input快照契约：私有HashMap只读视图或混合哈希坐标结构，防止下游再Map.copyOf退化。保留禁止null、外部修改不可见；对拍正负、狭长、横向和密集布局。

### GW-04：每owner重复处理完整构件（P2，收益待量）

PlanningChunkCompiler.java:207–218为各owner遍历component全部voxels采before；ChunkPlanCompiler.java:26–49重复componentHash，完整逻辑合并/连接解析后才裁owner。CanonicalCodec.java:103–120对完整构件序列化算hash。cellColumns/cellRealizations已有窗口缓存。

先加计数，再在窗口内一次校验不可变构件、一次解析完整邻接并分owner桶。不能先裁区块外体素再算楼梯/围栏连接。逐owner对拍hash、proof顺序、接缝和冲突，不改协议。

### GW-05：首次补建状态证明口径不一，失败仍结案（P1）

PlanningColumnView.state:48–52输出minecraft:stone{}等简写；PlanningChunkCompiler.java:214–218写入before，ChunkPlanCompiler.java:60–75原样生成proof。WallBodyBackfill.java:825经BlockCatalog.token(:86)取得带:fluid=...:be=...完整token。即便同材两字符串也不等；current==target更早跳过，不受此条影响。

原始日志2026-11-07-2.log.gz:44307有BACKFILL_CONFLICT：before=minecraft:stone{}，current=minecraft:dirt{}:fluid=minecraft:empty:be=false。日志确认格式不同，但材料也不同，不能叫“同石材真机复现”；同材必不等来自源码契约。

WallBodyBackfill.java:840写块返回false仅改fullyWritten，:841–843仍增加touched/written；:871写不完整marker，:877仍无条件SETTLED。drain:617–623移出pending并markDone。实体/marker失败也未形成可靠待处理终态。因此计数及队列完成不能代表全部成功落块。

用户要求适合首次plan优先：移除现状before比对导致的跳过，统一WallFeature:54–60与补建入口。replaceable:880–884另跳过方块实体和基岩，也需纳入首次强制施工政策；覆盖方块实体须正确清除/安装计划payload。仍保留合法高度、owner、KEEP和计划有效性。已完成同hash marker早退(:788–798)保留玩家修改。

写块失败、材料解析失败、实体/marker失败不能DONE；返回待处理或明确失败原因，保留重试上限及诊断。written只统计成功写入，最终盖章在必要步骤全部完成之后。强制施工不能省掉光照、高度图、客户端和存档成本。

## 4. 游戏内补建算法

nearestFirst:258–280每轮复制pending并全排序，实际按所有玩家平均位置计算距离，不是最近玩家。drain:585之后最多检查64项、结案4块、在途请求8块，每10tick一轮。150ms检查预算在排序之后，且只在区块之间检查，不是单块硬上限。

建议稳定Top-64最大堆，O(N log64)，每项距离只算一次，以原迭代序号处理并列，选出后排序64项；N≤64保留原排序，无玩家保留原前64。独立探针对80组视点及并列场景前64完全同序：

| pending | 全排序中位数 | 堆选择中位数 |
|---:|---:|---:|
| 64 | 13.4µs | 32.9µs |
| 512 | 81.3µs | 36.6µs |
| 4,096 | 635.8µs | 57.5µs |
| 65,536 | 13,363.6µs | 487.7µs |

6轮预热9轮记录，先原排序再堆，非严格交替/多进程基准，非游戏帧时。仅改善候选选择；单块长尾先量体素数、解析、写块、实体/marker及文件追加，再考虑section/体素游标。游标需计划代次、卸载/停服取消、票据归属和最后结案，不能随意截循环。

另可同plan缓存BlockSpec→BlockState、按XZ去重保护标记；不得跨注册表代次复用或省掉新会话足迹。markDone同步追加文件先测后改，不擅自异步丢数据。游戏内继续服务端方块接口，不能裸写ChunkAccess绕过客户端/光照语义。
