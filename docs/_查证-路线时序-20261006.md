## 0. 一句话结论（先给答案）

**「鸡生蛋」在数据依赖上不存在，在调度时序上真实存在。**

- **数据依赖层面不存在**：长城的地形输入是 `CpuTerrainOracle`，它由 `RandomState + NoiseChunk` 自建，**完全不读任何已生成区块**，是纯粹的「seed + 数据集」函数。因此理论上 **recipe → RouteShape → SegmentGeometry → SegmentPlan 全链路可以在一个区块都没生成的情况下算完**。
- **调度时序层面真实存在**：`WorldBootstrap` 只在 `prepareLevels HEAD` 之后的 `Frozen` 冻结完成时才允许 root pump 启动（`WorldBootstrap.java:201`），而 `prepareLevels` 之前原版 `setInitialSpawn` **已经同步生成了出生区区块（含 BIOMES 与 FEATURES）**（javap）。更关键的是 **recipe 的起点依赖原版 spawn，而原版 spawn 依赖已生成地形** —— 这是唯一一条真正闭环的蛋。
- **工程现状**：**没有任何 BIOMES 阶段钩子**。全 main 源码 grep `ChunkStatus.BIOMES` = 0 命中。现有树木抑制走的是 **FEATURES 阶段 + 树包围盒相交**（`TreeFeatureMixin`），**不需要群系，也不需要精确路线在 BIOMES 时可用**。

### 1.2 recipe 的输入依赖

`WorldRecipe` 是纯数据 record（`model/WallTypes.java:615-631`），字段为
`instance, wallId, seed, dimension, frozenSpawn, axis, bounds, config, terrainHash, paletteHash, templatesHash, recipeHash`。

其中：

| 字段 | 来源 | 是否依赖地形 |
|---|---|---|
| `seed` | `server.getWorldData().worldGenOptions().seed()`（`WorldBootstrap.java:76`） | ❌ 纯 seed |
| `frozenSpawn` | `bootstrap.spawnChosen(...)`，来自 `level.getSharedSpawnPos()`（`BootstrapSpawnMixin.java:20-21`） | ✅ **依赖地形**（见 §4.2） |
| `axis` | `RootSearch.finish()` 的 `Selection.axis()`（`RootSearch.java:143`） | ✅ **依赖地形采样** |
| `bounds` | `frozen.bounds()`，来自 `DimensionBounds(level.getMinBuildHeight(), level.getMaxBuildHeight(), 30_000_000)`（`CpuTerrainOracle.java:98-104`） | ❌ 维度常量 |
| `config` | `WorldBootstrap.defaultConfig()`，全常量（`WorldBootstrap.java:100-111`） | ❌ 常量 |
| `terrainHash` / `paletteHash` / `templatesHash` | `ProductionInputs.freeze`，来自 registry / 资源包 | ❌ 注册表与数据包 |
| `recipeHash` | `DeterministicHash.sha256(CanonicalCodec.recipe(provisional))`（`WorldBootstrap.java:261-264`） | 派生 |

**结论**：recipe 的**唯一地形相关字段是 `axis`（以及间接的 `frozenSpawn`）**；`axis` 由 `RootSearch` 选出。

### 1.3 已有存档的快捷路径

若 manifest 中已有 recipe，`WorldBootstrap.java:211-214` 走 `validateSaved(recipe, inputs)` → `publish(recipe)`，**跳过 RootSearch**。
但注意：**`ready` 仍然要等 `prepareLevels` 冻结**（`:201` 的 `inputs == null` 门），并不是「有存档就立刻 ready」。

## 2. 路线几何（RouteShape / SegmentGeometry / AnchorField）怎么算

### 2.1 三层几何

| 层 | 产出 | 计算者 | 依赖地形？ |
|---|---|---|---|
| L0 轴线 + 锚点场 | `AnchorField.lateral()/at()/carrier()` | 纯 Hermite + splitmix64 | ❌ **纯 seed+axis** |
| L1 路线 | `RouteShape` | `RidgePlanner`（读 `NaturalTerrainOracle`） | ✅ **必须地形** |
| L2 段几何 | `SegmentGeometry` | `HydrologyClassifier` + `geometry()` | ✅ **必须地形** |
| L3 段计划 | `SegmentPlan` | `HeightContractPlanner.solve(...)` + `SiteScheduler` | ✅ **必须地形** |

### 2.2 `AnchorField` —— 完全纯函数（关键发现）

`planning/AnchorField.java`：

- `lateral(long boundaryIndex)`（`:24-29`）：
  ```java
  return boundaryIndex == 0 ? 0 : 256L * (DeterministicHash.bounded(
          DeterministicHash.fields(recipe.seed(), "anchor", boundaryIndex), 769) - 384);
  ```
  **只吃 `recipe.seed()` 与下标**。零世界访问。
- `at(long boundaryIndex)`（`:31-40`）：调 `lateral` + `tangent` + `world(u,b)`，纯。
- `carrier(long segment, int localUQ8)`（`:42-62`）：Hermite 基函数 + `BigInteger` 定点除法，纯。
- `world(long u, long b)`（`:68-79`）：把 `(u,b)` 投到 `recipe.axis()` 上，纯（只用 `axis.origin/exQ30/ezQ30` 与 `bounds.horizontalLimit`）。
- `checkEnvelope(...)`（`:81-98`）：解析求 Hermite 极值，**超过 `512 * 256` 抛 INVALID_RESOURCE**（`:95-97`）——即 **carrier 侧向包络硬上限 ±512 格**。

**结论：`AnchorField.lateral()` / `at()` / `carrier()` 是纯 seed 函数（不读世界）—— 问题 3 的答案是「是」。**
但它们的输入包含 `recipe.axis()`，**而 axis 本身不是纯 seed 的**。所以「给定 seed 直接调 `AnchorField.lateral()`」可以，但「给定 seed 直接得到 carrier 位置」不行——还差一个 axis。

这也与测试一致：`src/test/java/local/plaincraft/greatwall/planning/AnchorProjectionTest.java:17-22` 直接用 `PlanningFixtures.recipe(seed)` 构造 `AnchorField` 并对同 seed 复现性做断言，**全程无 oracle、无世界**。

### 2.3 `RidgePlanner` —— 必须读地形（蜿蜒搜索）

`planning/RidgePlanner.java`：

- `begin(SegmentKey, NaturalTerrainOracle)`（`:35-46`）：先校验 `oracle.fingerprint().equals(recipe.terrainHash())`（`:39-41`），再把 `cursor.first/last = anchors.at(...)`。
- `boundaryStep`（`:70-80`）：`sample(c, anchor.point(), SampleKind.REFERENCE, true)` → 读地形取 `groundTopY` 定 `walkY = groundTopY + 20`。
- `searchStep`（`:82-144`）：这是蜿蜒核心。对每 16 格一步，枚举 `DELTAS = {-12,-8,-4,0,4,8,12}`（`:19`），在每个候选中心周围 **9 点采样**（`OFFSETS`，`:20-22`），用
  ```java
  long score = 4 * ridge + 2 * prominence - 5 * slope - 2 * turn - 8 * wet - departure;
  ```
  （`:134`）打分选优。`ridge`/`prominence` 全部来自 `groundTopY`/`waterTopY`（`:127-132`）。
- `sample(...)`（`:158-173`）：真正落地点，`c.oracle.begin/advance/finish`。

**结论：`RidgePlanner` 的蜿蜒搜索确实读地形（经 `NaturalTerrainOracle`）—— 问题 4 的答案是「是」。**
但**这个「地形」不是区块，而是 CPU 噪声预言机**（见 §3，这是本报告最关键的一点）。

### 2.4 `PlannerScheduler` —— 编排层，不改变依赖性质

- 构造（`:74-114`）：`this.anchors = new AnchorField(recipe); this.ridge = new RidgePlanner(recipe, anchors);`（`:105`）。
- `requireRoute`（`:117-124`）→ `RouteJob`（`:703-714`）→ `ridge.begin/advance/finish`。
- `requireGeometry`（`:126-135`）→ `HydroJob`（`:716-737`）→ `hydrology.begin(...)`（读地形）。
- `requirePlan`（`:137-164`）→ `ContractJob`（`:739-764`）→ `oracle.begin(...)`（`:754`，读地形）。
- `requireWindow`（`:166-207`）：**这一步只用 `Projection.axisUQ8` 与叉积判距，不读地形**；它用
  ```java
  long lateral = (512L + 512 + 96 + marginBlocks) * 256;   // :184
  if (minB > lateral || maxB < -lateral ...) return empty; // :185
  ```
  做**纯解析式粗筛**，再去 `requirePlan`。
- `safeSegment`（`:540-553`）：注释明写 `// 512 carrier + 512 ridge + 96 component + 48 reference side-column envelope.`，`radius = 1168L * 256`（`:544`）。
  注意：该式检查的是**轴上点**（`u = index * 2048 * 256` 投到 `recipe.axis()`）到世界水平边界的距离，即 `1168 = 512(carrier) + 512(ridge) + 96(component) + 48(reference)` **是相对于轴线（axis）的垂直半宽**，不是相对于 carrier 的。

**结论：`PlannerScheduler` 中已存在「不读地形的粗筛」（`requireWindow` 的侧向包络测试），但它需要 recipe 才能工作。**

### 2.5 `PrefixSummaryIndex` —— 不是粗粒度资产

`planning/PrefixSummaryIndex.java:81-92` 的 `reduce(PrefixSummary, SegmentGeometry)` 是**对精确 `SegmentGeometry` 的有序归约**（累加弧长 + 传播 terminal），输入必须是已算好的 geometry。

**结论：`PrefixSummaryIndex` 不是「不读地形的粗粒度长城范围」——它是最精细的依赖者之一。**（问题 6 的否定证据）

## 3. ★ 决定性发现：`CpuTerrainOracle` 是 seed 纯函数，不读区块

这是本次查证最重要的结论，直接决定「鸡生蛋」的性质。

### 3.1 输入冻结：只读维度/注册表/seed

`terrain/CpuTerrainOracle.java:90-105`：

```java
public static FrozenInput freeze(ServerLevel level, String fingerprint) {
    if (!level.getServer().isSameThread()) { throw ... }
    if (!(level.getChunkSource().getGenerator() instanceof NoiseBasedChunkGenerator generator)) { throw ... }
    return new FrozenInput(generator.generatorSettings().value(),
            level.registryAccess().registryOrThrow(Registries.NOISE).asLookup(),
            ((NoiseGeneratorAccess) (Object) generator).greatwall$fluidPicker().get(), generator.getBiomeSource(),
            new DimensionBounds(level.getMinBuildHeight(), level.getMaxBuildHeight(), horizontalLimit),
            level.getSeed(), fingerprint);
}
```

**逐项核对：`getChunkSource().getGenerator()`（拿生成器对象）、`registryAccess()`、`getMinBuildHeight()`、`getMaxBuildHeight()`、`getSeed()`。**
**没有任何 `getChunk` / `getChunkNow` / 区块内容读取。**

### 3.2 构造：自建 RandomState

`CpuTerrainOracle.java:77-87`：
```java
randomState = RandomState.create(settings, frozen.noises(), frozen.seed());   // :85
```
`RandomState` 由 `settings + noises + seed` 生成，**与任何区块无关**。

### 3.3 采样：自建 NoiseChunk

- `coarse(Cursor)`（`:177-191`）：直接
  ```java
  randomState.router().initialDensityWithoutJaggedness().compute(new DensityFunction.SinglePointContext(...));
  ```
  纯密度函数求值。
- `reference(Cursor)`（`:193-246`）：`c.chunk = new NoiseChunk(1, randomState, cellX, cellZ, noise, DensityFunctions.BeardifierMarker.INSTANCE, settings, fluidPicker, Blender.empty())`（`:197-199`）。
  **自己 new 了一个 NoiseChunk，半径 1，`Blender.empty()`** —— 即「在真空里生成地形」，**不借任何已生成区块**。

### 3.4 群系也来自纯采样

`CpuTerrainOracle.java:248-257`：
```java
String biome = biomeSource.getNoiseBiome(Math.floorDiv(c.x, 4),
        Math.floorDiv(c.groundTop, 4), Math.floorDiv(c.z, 4), randomState.sampler())...
```
用的是 **`BiomeSource.getNoiseBiome(qx,qy,qz, sampler)`** —— 气候参数纯函数查询，**不是读区块的群系数组**。

> 这也与既有规格一致：`docs/S1C-接线源码核实.md:332`「生物群系只调用 `getNoiseBiome`，不用 `possibleBiomes()`」；`docs/S1C-接线源码核实.md:333`「生产规划不调用单列不可切片的 `getBaseColumn`」。

### 3.5 唯一读区块的地方是结构筛，且只在 BIOMES 之前

`RootSearch` 的 `NativeRootStructureScreen` 会通过 `StructureLease` 请求区块：

- `NativeRootStructureScreen.java:69`：`ChunkStatus.STRUCTURE_REFERENCES`
- `NativeRootStructureScreen.java:78`：`ChunkStatus.STRUCTURE_STARTS`
- `StructureLease.java:31-33` 显式限制：
  ```java
  if(status!=ChunkStatus.STRUCTURE_STARTS&&status!=ChunkStatus.STRUCTURE_REFERENCES)
      throw new IllegalArgumentException("root lease cannot request terrain/features/light");
  ```

**即：root 搜索过程中唯一触碰区块的地方，也只请求 `STRUCTURE_STARTS`/`STRUCTURE_REFERENCES` —— 这两个状态在 `BIOMES` 之前（javap，见 §4.1），因此不触发群系分配。**

### 3.6 结论

> **给定 seed + 冻结的数据集/注册表，`CpuTerrainOracle` 可以在零区块生成的前提下产出任意 (x,z) 列的 `groundTopY / waterTopY / bedTopY / biomeKey`。**
> 因此 **recipe → RouteShape → SegmentGeometry → SegmentPlan 全链路的「地形输入」并不需要世界里的地形**。

## 4. 时序：区块状态序与启动序（javap 一手取证）

### 4.1 `ChunkStatus` 声明顺序（决定性）

对 named jar `net.minecraft.world.level.chunk.status.ChunkStatus` 的 `<clinit>` 反汇编，`register(...)` 调用顺序为：

```text
empty → structure_starts → structure_references → biomes → noise → surface
      → carvers → features → initialize_light → light → spawn → full
```

（javap：`ChunkStatus.<clinit>`，偏移 30/45/62/79/96/113/130/147/164/181/198/215 依次 `ldc` 名称 + `invokestatic register` + `putstatic`；
字段顺序亦为 `STRUCTURE_STARTS, STRUCTURE_REFERENCES, BIOMES, NOISE, SURFACE, CARVERS, FEATURES, INITIALIZE_LIGHT, LIGHT, SPAWN, FULL`。）

**推论（关键）：`BIOMES` 在 `NOISE / SURFACE / CARVERS / FEATURES` 之前。**
所以「在地形生成后覆写群系数组」这个措辞在时序上是不准确的：**群系数组是在噪声地形写入之前就定下的**。

同时 `ChunkStatusTasks`（javap）确认各状态对应的任务：
```text
BIOMES   → generateBiomes   → ChunkGenerator.createBiomes(...)
NOISE    → generateNoise    → fillFromNoise(...)
SURFACE  → generateSurface  → buildSurface(...)
CARVERS  → generateCarvers  → applyCarvers(...)
FEATURES → generateFeatures → primeHeightmaps(...) + applyBiomeDecoration(...)
```

### 4.2 原版启动序：`setInitialSpawn` 会生成区块

对 `net.minecraft.server.MinecraftServer` 反汇编：

- `createLevels(...)` 内偏移 **216** 处 `invokestatic setInitialSpawn(...)`；
- 上层流程偏移 69 `createLevels` → 78 `prepareLevels`。

`setInitialSpawn` 本体（javap，`private static void setInitialSpawn`）：
1. 偏移 32-41：`ServerChunkCache.randomState().sampler().findSpawnPosition()` → 得到搜索中心（**纯气候函数，不生成区块**）；
2. 偏移 73-96：`level.getHeight(Heightmap.Types.WORLD_SURFACE, ...)`（**此调用会生成区块**）；
3. 偏移 134-280：11×11 螺旋循环，偏移 194 `PlayerRespawnLogic.getSpawnPosInChunk(level, chunkPos)`。

`PlayerRespawnLogic.getSpawnPosInChunk`（javap）→ 偏移 38 `getOverworldRespawnPos(level, x, z)` → 偏移 17：
```text
invokevirtual Method net/minecraft/server/level/ServerLevel.getChunk:(II)Lnet/minecraft/world/level/chunk/LevelChunk;
```
**`ServerLevel.getChunk` 返回 `LevelChunk`（FULL 状态）** —— 即出生点搜索**同步生成出生区区块至 FULL，其中包括 BIOMES 与 FEATURES 两个步骤**。

**推论：在 `BootstrapSpawnMixin`（`setInitialSpawn` RETURN）记录 spawn 之前，原版已经跑完了一批区块的 BIOMES + FEATURES。而此时 recipe 必然不存在**（root pump 甚至还没被允许启动，因为 `prepareLevels` 尚未进入）。

### 4.3 `prepareLevels` 与 root pump 的时序

`prepareLevels` 本体（javap）：
- 偏移 0-37：读 `getSharedSpawnPos()`、`progressListener.updateSpawnPos(...)`；
- 偏移 95-120：`while (getTickingGenerated() < diameter²) { nextTickTimeNanos = ...; waitUntilNextTick(); }` —— **生成出生区区块**。

`MinecraftServerProbeMixin.java:12-15` 在 **`prepareLevels` HEAD** 注入 → `WorldServices.warming(...)` → 冻结 + `prepareLevelsEntered`。

**所以：root pump 的启动点（`prepareLevels HEAD`）早于 `prepareLevels` 内部的出生区生成循环，但晚于 `setInitialSpawn` 内部的出生点搜索生成。**

### 4.4 现有代码里**没有** BIOMES 阶段钩子

对 `src/` 全域 grep `ChunkStatus.BIOMES` → **0 命中**。
`VanillaGateMixin.java` 只挂两个状态：

```java

if (step.targetStatus() != ChunkStatus.FEATURES) return original.call(...);  // :40
```

- `INITIALIZE_LIGHT`（`:34-39`）→ `services.beforeProductionLight(...)` → `ProductionSession.beforeLight` → `bootstrap.beforeRecipe(key)` + `barrier().beforeLight(...)`
- `FEATURES`（`:40-55`）→ `services.featureLease(dimension, pos.x, pos.z)` 申请植被规划租约

**`BIOMES` 完全不受长城门控，按原版流程走完。**

## 5. 现有树木抑制机制：**不依赖群系，也不依赖路线在 BIOMES 时可用**

这是回答「有没有绕法」时最相关的既有事实。

### 5.1 机制

`mixin/TreeFeatureMixin.java:15-33`：注入 `TreeFeature.place(...)` 的 **HEAD**，`cancellable = true`。

`generation/TreeBoundsCatalog.java:91-111` 的 `vanilla(...)`：从冻结目录取树冠半径，**取不到时退化为保守半径**（`:98-106`，`conservativeRadius()` 见 `:118-120`），返回树 origin ± radius 的完整包围盒。

`generation/VegetationGuard.java:54-62`：把该包围盒与**已发布的走廊快照**做 AABB 相交；**快照缺失直接抛 `MISSING_FEATURES_PLAN`**（`:56`）。

### 5.2 走廊快照从哪来

`ProductionSession.java:415-448`（`FeatureSlot.start()`）：

```java
  → vegetation.publish(owner, plans)                                    // :453
```

而 `VegetationGuard.publish`（`:14-52`）用 `plan.stations()` 与 `plan.sites()` 生成包围盒（主墙 ±44、出口 ±exitMargin、站点 ±32）。

**即：走廊快照来自 `SegmentPlan`（L3），是精确路线，且依赖地形样本。**

### 5.3 与群系无关

`TreeFeatureMixin` 的判断链里**没有任何 biome 读取**。它靠「树的完整包围盒 ∩ 走廊包围盒」做抑制，这正是它能覆盖**所有 mod 的树**（只要树最终走 `TreeFeature.place`）的原因。

### 5.4 但它被 `beforeRecipe` 卡住

`FeatureSlot.start()` 第一步就是 `bootstrap.beforeRecipe(owner)`（`:416`），而 `WorldBootstrap.beforeRecipe`（`:127-134`）在非 earlyDomain 时 **必须等 `ready`**：

```java
return authorized.thenCompose(value -> {
    active();
    if (mayPassBeforeRecipe(requested)) return CompletableFuture.completedFuture(null);
    return ready.thenApply(recipe -> (Void) null);      // :132 —— 等 recipe
}).copy();
```

**所以现有 FEATURES 抑制机制本身也依赖 recipe already ready。** 它与「BIOMES 阶段覆写群系」面临同一个时序约束，只是它发生在更晚的 FEATURES 阶段，因此有更多时间余量。

## 7. ★ 明确回答：鸡生蛋问题是否存在？

### 7.1 数据依赖：**不存在**

理由链（全部可复核）：

1. `CpuTerrainOracle.freeze(level, fp)` 只读 generator / registry / minY / maxY / seed（`CpuTerrainOracle.java:90-105`）。
2. 构造只做 `RandomState.create(settings, noises, seed)`（`:85`）。
3. 采样自建 `new NoiseChunk(1, randomState, ...)`（`:197-199`）。
4. `RidgePlanner` / `HydrologyClassifier` / `HeightContractPlanner` 的地形输入**全部**经 `NaturalTerrainOracle`（`RidgePlanner.java:166-170`；`HydrologyClassifier.java:370-373`；`PlannerScheduler.java:754-756`），而生产实现就是 `CpuTerrainOracle`（`ProductionInputs.java:24,35`）。
5. `RootSearch` 锚定 `Selection.axis` 所用的粗筛/足印/轴/入口四阶段（`RootSearch.java:182-317`）只调 `read(oracle, ...)`（`:327-338`）。
6. 结构筛只请求 `STRUCTURE_STARTS/REFERENCES`（`StructureLease.java:31-33`），两者都在 `BIOMES` 之前（§4.1 javap）。

> **所以「要算路线得先有地形」这句话里的「地形」，指的是噪声可预测地形，不是已生成区块。**
> **一个区块都不生成，也能算出完整 recipe 与 RouteShape。**

### 7.2 调度时序：**存在**，且有两个具体卡点

**卡点 A（真闭环）：recipe 依赖原版 spawn，原版 spawn 依赖已生成区块。**

- `RootSearch` 构造要求非空 `spawn`（`RootSearch.java:49,90`），`ringPoint`/`axis` 全部以 spawn 为中心（`:354-367`）。
- `spawn` 来自 `level.getSharedSpawnPos()`（`BootstrapSpawnMixin.java:20-21`）。
- 而 `setInitialSpawn` 内部会 `ServerLevel.getChunk(...)`（javap，§4.2）→ **同步生成出生区区块至 FULL（含 BIOMES 与 FEATURES）**。

> **这是一个真正的蛋：城墙路线 ← 原版 spawn ← 已生成的出生区地形（含群系）。**
> 出生区那批区块的群系数组，在 recipe 存在之前就已写完，**无解**。

**卡点 B（可缓解）：`ready` 只在 `prepareLevels` 冻结后才可能完成。**

- `WorldBootstrap.java:201`：`if (inputs == null || authorization.saved().isEmpty() && !spawn.containsKey("chosen")) return;`
- `inputs` 由 `prepareLevelsEntered` 灌入（`:157-171`），而 `prepareLevelsEntered` 只在 `prepareLevels HEAD` 触发（`MinecraftServerProbeMixin.java:12-15`）。
- 即使有 saved recipe，`publish` 也要等 `inputs != null`（`:201` 短路顺序）。

> 但 `prepareLevels HEAD` 早于其内部的出生区生成循环（javap，§4.3），且 root 搜索是异步 lane（`WorldBootstrap.java:227-269`），
> 而长城本体在 800..1500 格环带外（`RootSearch.java:45`），远在默认出生半径之外。
> **所以对「长城本体附近的区块」，recipe 在实际游玩中通常是先于这些区块的 BIOMES 就绪的 —— 但这是时序余量，不是保证。**

### 7.3 逐事件时序对照表

| 事件 | 触发点 | 此刻 recipe 是否可能就绪 |
|---|---|---|
| 世界创建 | `createLevels` | ❌ 不存在（`authorized` 刚发出，`frozen` 为空） |
| 出生点气候搜索 | `Climate.Sampler.findSpawnPosition()` | ❌（且此步不生成区块） |
| 出生区区块 → BIOMES/FEATURES | `setInitialSpawn` → `getChunk(...)` (javap) | ❌ **必然不存在**（`prepareLevels` 尚未进入） |
| 记录 spawn | `BootstrapSpawnMixin` RETURN | ❌ |
| 冻结 inputs | `prepareLevels HEAD` | ❌ |
| root pump 启动 | 冻结后异步 | ⏳ 计算中 |
| recipe `ready` | `publish()` | ✅ （此后） |
| `prepareLevels` 出生区循环 | HEAD 之后 | ⏳ 竞态 |
| 玩家外扩触发远区块 BIOMES | 视距/票据 | ✅ 通常已就绪（**未验证**实际耗时分布） |

## 8. 绕法评估

### 8.1 绕法 1（推荐，已存在）：不做群系覆写，继续用 FEATURES 阶段的树包围盒抑制

- **现状**：`TreeFeatureMixin` 已在生产接线中存在（`plaincraft_great_wall.mixins.json` 的 `mixins` 列表含 `TreeFeatureMixin`）。
- **优点**：不碰群系；对**所有** mod 的树生效（只要走 `TreeFeature.place`）；语义是「树的完整包围盒 ∩ 长城走廊」。
- **约束**：需要 `VegetationGuard` 快照，而快照需要 `SegmentPlan`（`ProductionSession.java:433,453`），因此仍需 recipe。
- **残留风险**（既有，非本次新增）：不走 `TreeFeature.place` 的第三方写树路径不受保护；`TreeBoundsCatalog` 对编码失败的树 WARN 后跳过（`TreeBoundsCatalog.java:60-78` 用户授权保留项）。

### 8.2 绕法 2：粗粒度走廊替代精确路线 —— **仅在已有 recipe 时可行**

**给定 recipe（seed + axis）：**

- `AnchorField.carrier(seg, u)` **零地形读取**即可算出精确中心线（`AnchorField.java:42-62`）。
- 中心线到实际墙体的侧向偏差有**硬上限**：
  - carrier 包络 ≤ 512 格（`AnchorField.java:95-97`）
  - ridge 搜索偏移 ≤ 512 格（`RidgePlanner.java:97-99` 拒绝 `|candidateOffset| > 512*256`；`:105` 同；`:263-265` `|residual| > 512*256` 则 fallback）
  - 构件 ≤ 96、参考侧列 ≤ 48（`PlannerScheduler.java:543-544` 注释与 `radius = 1168L * 256`）
- **因此「轴线(axis) ± 1168 格」是一个可靠的过近似走廊**，且 `PlannerScheduler.requireWindow`（`:184-185`）已在用同一套界做粗筛（`(512L + 512 + 96 + marginBlocks) * 256`）。
  **注意量取基准**：`1168` 是相对**轴线**的半宽，不是相对 carrier 的。若要相对 carrier 表述，需再加 carrier 自身包络 ±512（`AnchorField.java:95-97`），即 **carrier ± 1680 格**（512+512+512+96+48）；反过来 carrier 相对 axis 的偏移也已被 `checkEnvelope` 限在 ±512 内。

**精度评估：**

| 方案 | 需要 recipe？ | 需要世界地形？ | 精度 |
|---|---|---|---|
| `axis ± 1168` | ✅ | ❌ | **最紧的可靠粗走廊**，半宽 1168 格（≈73 区块）；与 `safeSegment`/`requireWindow` 同源 |
| `axis ± 656`（512+96+48） | ✅ | ❌ | 更紧，但**未把 ridge 蜿蜒 512 计入 → 不安全**，仅列作对比 |
| `carrier`（精确中心线） | ✅ | ❌ | 中心线精确，但**偏移范围 ±512 未知** → 实际走廊仍需 ±1680 |
| `RouteShape`（逐 16 格点） | ✅ | ⏳ 需 CPU 采样（非区块） | **精确路线**，逐格 |
| 实际墙体（`SegmentPlan` 站点 + 构件） | ✅ | ⏳ 同上 | **精确到方块** |

> **注意**：`RouteShape` 需要的只是 CPU 采样，**不需要世界地形**。所以「精确路线」在数据上是可得的，瓶颈纯粹是**算力与时序**（`columnBudget = 150000`，`WorldBootstrap.java:109-110`）。

**给定 seed 但无 recipe：**

- ❌ **无法给出任何有用的走廊**。`axis` 是 4 半径 × 36 角度 × 5 轴偏 = **720 个候选**（`RootSearch.java:45-48`）中由地形筛出的一个（`:182-317`）。
- 唯一纯 seed 可知的是**候选环带**：`inRing` 要求起点落在 spawn 的 `800..1500` 环内（`RootSearch.java:394-397`），且朝向必须离开早期域（`:256-260`）。
- 但这只界定「起点在哪」，**不界定「墙往哪走」**（墙从起点沿 axis 一直延伸到世界边界，`PlannerScheduler.safeSegment` 逐段判，`:540-553`）。
- **所以纯 seed 的粗粒度范围 ≈ 「spawn 周围 (1500 + 1168 + 512) 格内的一切」—— 对群系覆写毫无实用价值。**

### 8.3 绕法 3：把 freeze + root search 提前到「任何区块生成之前」

- **数据上可行**：oracle 不需要区块（§3）。
- **阻断点**：`spawn` 必须来自原版 spawn 搜索（`RootSearch.java:49,90`），而该搜索本身生成 FULL 区块（§4.2）。
- **可能的破法**（**均为本次未验证的设计建议，不是已验证结论**）：
  - (a) 改用 `Climate.Sampler.findSpawnPosition()` 作为 root 圆心，**不等 `setInitialSpawn` 的最终 spawn**。但 `findSpawnPosition` 只是搜索中心，与最终 spawn 可能相距数百格 → 会改变长城选位语义，需用户裁定。
  - (b) 接受出生区一小批区块无长城群系，只对远区块生效。
  - (c) 首次进入世界时先把 recipe 算完并持久化，下次进世界（`manifest.read()` 命中）即可在 `BIOMES` 前拿到路线 —— **但 `ready` 仍要等 `prepareLevels`**（`WorldBootstrap.java:201`）。要真正生效需把 `publish` 从 `prepareLevels` 依赖中解耦，**未验证是否安全**（palette/templates hash 的校验在 `validateSaved`，`:272-278`）。
- **未验证**：overworld LOAD 与 `setInitialSpawn` 之间原版是否还有其它区块生成点。本次只核实了 `createLevels` 内偏移 216 的 `setInitialSpawn` 调用。

### 8.4 绕法 4（若坚持群系覆写）：必须在**非 BIOMES** 的时机改写群系

由于采用「专属群系 features 列表为空」来抑制树，需要**在 `applyBiomeDecoration` 读群系之前**写入群系数组。javap 确认读群系的位置是：

`ChunkGenerator.applyBiomeDecoration`（javap）：
```text
偏移 141-158：ChunkPos.rangeClosed(chunkPos, 1).forEach(...)   // 收集 3×3 邻域的群系
偏移 163-172：decorationBiomes.retainAll(biomeSource.possibleBiomes())
偏移 446-460：generationSettingsGetter.apply(biome).features()  // 逐装饰步读该群系的 features 列表
偏移 643-651：PlacedFeature.placeWithBiomeCheck(...)
```

**关键技术事实（javap）：**

1. **群系集合来自 3×3 邻域**（`ChunkPos.rangeClosed(chunkPos, 1)`），不只是本区块。
2. **`retainAll(biomeSource.possibleBiomes())`** —— 自定义群系若不在 `possibleBiomes()` 中会被剔除。这与既有红线冲突：`docs/S1-S5实施规格/README.md:40` 的 R3「不调用或修改 `possibleBiomes()`」；`docs/S1-城墙本体.md:1523` 明文「不得复制其 `possibleBiomes` Mixin」。
3. **`placeWithBiomeCheck` 本体不含群系查询**（javap：仅构造 `PlacementContext` 后调 `placeWithContext`）。**群系过滤由放置修饰符 `minecraft:biome` 完成**（→ `BiomeFilter`）。

**由此得到一条重要限制（回答「能否抑制所有 mod 的树木生成」）：**

> 即使把长城走廊内所有区块的群系数组覆写成「无树群系」，**邻域 3×3 中森林群系的 tree `PlacedFeature` 仍会进入同一个 `IntArraySet`，并在本区块内放置**（javap 偏移 415-539：群系是逐个 union 进集合的）。
> **因此「群系数组覆写」无法单独完成「抑制所有 mod 树木生成」；它必须与 `TreeFeatureMixin` 式的包围盒抑制叠加。**
> （这一条对本次任务目标影响很大，建议优先评估。）

### 8.5 绕法对比小结

| 绕法 | 能否解决「BIOMES 时拿到路线」 | 代价 / 阻断 |
|---|---|---|
| 1. 沿用 FEATURES 包围盒抑制 | 不需要路线在 BIOMES 可用 | 已实现；需 recipe（FEATURES 时通常已就绪） |
| 2. `axis ± 1168` 粗走廊 | ✅ 但需 recipe | 半宽 1168 格（相对轴线），群系覆写面积巨大 |
| 3. 提前 freeze + root search | ⚠️ 数据可行 | 被 spawn↔generated-terrain 闭环卡住（§7.2 卡点 A） |
| 4. 群系覆写（叠加 1） | ⚠️ 需解决 §8.4 的 3×3 union | 撞 R3 红线；且单独不足以抑制树木 |

## 10. 结论摘要

1. **recipe 从哪来**：`setInitialSpawn` 记录 spawn → `prepareLevels HEAD` 冻结 inputs → root pump → `RootSearch` 四阶段（粗筛/足印/轴/入口）选出 `Selection.axis` → 与 seed/bounds/config/hash 一起冻结成 `WorldRecipe`（`WorldBootstrap.java:194-283`；`RootSearch.java:100-145`）。

2. **路线几何怎么算**：`AnchorField` 是**纯 seed+axis 的 Hermite 载体**（`AnchorField.java:24-79`）；`RidgePlanner` 在其上做**读地形的蜿蜒搜索**（`RidgePlanner.java:82-144`）。

3. **`AnchorField.lateral()/at()/carrier()` 是否纯 seed**：**是，完全不读世界**（`AnchorField.java:24-62`）。但它们还差一个 `recipe.axis()`，而 axis 不是纯 seed 的。

4. **`RidgePlanner` 是否读地形**：**是**（9 点 COARSE 采样，`RidgePlanner.java:118,158-173`）。**但它读的是 `CpuTerrainOracle` 的自算噪声，不是世界区块。**

5. **给定 seed 能否不读地形算出「长城经过哪些 chunk」**：
   - **无 recipe**：❌ 不能。axis 是 720 候选中的地形筛选结果（`RootSearch.java:45-48,182-317`）。
   - **有 recipe**：⚠️ 只能给出**粗走廊**。carrier 是精确中心线，但蜿蜒偏移未知；可靠上界是 **轴线 ± 1168 格**（`AnchorField.java:95-97` carrier 包络 512 + `RidgePlanner.java:97-99,263-265` ridge 偏移 512 + `PlannerScheduler.java:543-544` 构件 96 与参考侧列 48）。精确路线需要 CPU 采样。

6. **现有代码里的粗粒度范围**：
   - ✅ `SpawnDomain`（earlyDomain）：仅出生探测依赖域，`MAX_CHUNKS = 4096`（`SpawnDomain.java:12,16-32`），**与长城本体无关**。
   - ✅ `PlannerScheduler.requireWindow` 的侧向包络粗筛（`:184-185`）：**需 recipe**，是「不读地形的粗筛」但不是「粗粒度长城范围」。
   - ✅ `AnchorField` 的 ±512 包络（`:95-97`）：需 recipe。
   - ❌ `PrefixSummaryIndex`：**不是**粗粒度资产，它归约精确 `SegmentGeometry`（`:81-92`）。
   - ❌ **不存在**「纯 seed 的粗粒度长城范围」。

7. **鸡生蛋是否存在**：
   - **数据依赖上不存在** —— `CpuTerrainOracle` 是 seed 纯函数（`CpuTerrainOracle.java:85,197-199`），全链路可在零区块下算完。
   - **调度时序上存在** —— (A) recipe ← spawn ← 已生成出生区地形（javap，闭环）；(B) `ready` 被 `prepareLevels` 冻结卡住（`WorldBootstrap.java:201`）。
   - **工程上无 BIOMES 钩子**，且 `BIOMES` 在 `NOISE/SURFACE/FEATURES` **之前**（javap，§4.1）——「地形生成后覆写群系数组」这个前提本身不成立。

8. **最省力绕法**：**不做群系覆写，沿用已有的 FEATURES 阶段树包围盒抑制**（`TreeFeatureMixin.java:15-33` + `VegetationGuard.java:54-62`）——它对所有走 `TreeFeature.place` 的树生效，不依赖群系。若必须做群系覆写，须叠加该机制，因为 `applyBiomeDecoration` 的 3×3 邻域群系 union（javap）会让邻区块的森林群系继续在本区块放树。
