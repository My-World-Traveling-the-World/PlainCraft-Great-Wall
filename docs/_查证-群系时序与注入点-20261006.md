## 0. 结论摘要（先读这段）

| # | 问题 | 结论 |
|---|---|---|
| 1 | `ChunkStatus` 顺序 | `EMPTY → STRUCTURE_STARTS → STRUCTURE_REFERENCES → BIOMES → NOISE → SURFACE → CARVERS → FEATURES → INITIALIZE_LIGHT → LIGHT → SPAWN → FULL`（共 12 个）。`BIOMES` 在下标 3，`FEATURES` 在下标 7。 |
| 2 | 群系何时写入 chunk | `ChunkStatusTasks.generateBiomes` → `ChunkGenerator.createBiomes` → `NoiseBasedChunkGenerator.doCreateBiomes` → `ChunkAccess.fillBiomesFromNoise`。**在 FEATURES 之前**（BIOMES 是下标 3，FEATURES 是下标 7，中间还隔 NOISE / SURFACE / CARVERS）。 |
| 3 | **树木生成读哪个群系数据** | **读 chunk 里存的 biome 数组**，不是重新采样 `BiomeSource`。✅ 覆写 biome 数组**在原理上**能让树木服从新群系。 |
| 3b | **但是有一个致命前提**（本次最重要的新发现） | `applyBiomeDecoration` 在读完数组后，会执行 `biomeSet.retainAll(biomeSource.possibleBiomes())`。**若新群系不在 `possibleBiomes()` 里，它会被整条剔除，该区域将「一个 feature 都不派发」**——连树都不会长，但不是因为"服从了新群系"，而是因为群系被删空了。 |
| 5 | 金圣域 HEAD 注入时机 | 在 feature 派发**之前**（`@At("HEAD")`，而派发集合在方法体偏移 132–158 才构建）。它覆写的数组**会被**随后的派发读取（`getBiomes()` 返回的是 `fillBiomesFromNoise` 重建后的新容器）。**但金圣域之所以能生效，是因为它同时还有 `BiomeSourceMixin` 注入 `possibleBiomes`**——两者缺一不可。 |
| 6 | 更早/更晚的注入点 | `createBiomes`（BIOMES）、`buildSurface`（SURFACE）、`applyCarvers`（CARVERS）都在 FEATURES 之前，覆写数组都能传播到树木派发；但都各自有代价（见 §7）。 |

**一句话**：覆写 biome 数组能让树木服从新群系，**但只有在「新群系已是 `biomeSource.possibleBiomes()` 成员」时成立**；否则 `retainAll` 会把新群系删掉，导致该区块 **feature 全部静默跳过**。

### 3.4 🔴 致命前提：`retainAll(biomeSource.possibleBiomes())`

`applyBiomeDecoration` 偏移 `163–177`（原文见 §3.1）：

```java
biomeSet.retainAll(biomeSource.possibleBiomes());   // ← 这一行决定了覆写是否"有意义"
```

- `biomeSet` 就是刚从 3×3 区块数组收集来的 `ObjectArraySet<Holder<Biome>>`。
- `retainAll` 是**按 `Holder` 身份**求交集：**不在 `possibleBiomes()` 里的群系会被整条删除**。
- 删除之后，偏移 `424` 的 `for (Holder<Biome> biome : biomeSet)` 就遍历不到它，
  于是 `stepFeatures` 为空 → `PlacedFeature.placeWithBiomeCheck` **一次都不会被调用**。

全 jar 扫描「引用 `possibleBiomes` 的类」只有 7 个，可用于确认没有第二条路径：
`BiomeSource`、`MultiNoiseBiomeSource`、`FixedBiomeSource`、`TheEndBiomeSource`、
`CheckerboardColumnBiomeSource`、`ChunkGenerator`、`ChunkGeneratorStructureState`。

其中 `ChunkGenerator` 的两处用法：
1. `applyBiomeDecoration` 的 `retainAll`（上面这条）；
2. 构造器里 `featuresPerStep = Suppliers.memoize(...)`，body 为
   `method_44215(biomeSource, generationSettingsGetter)`：
   ```
   0: aload_0
   1: invokevirtual BiomeSource.possibleBiomes:()Ljava/util/Set;
   4: invokestatic List.copyOf:(Ljava/util/Collection;)Ljava/util/List;
   8: invokedynamic ...
  14: invokestatic FeatureSorter.buildFeaturesPerStep:(Ljava/util/List;Ljava/util/function/Function;Z)Ljava/util/List;
  17: areturn
   ```
   → **`featuresPerStep` 只包含 `possibleBiomes()` 里的群系的 feature**。

⇒ **如果新群系不在 `possibleBiomes()` 里**：
- `retainAll` 把它从派发集合里删掉 → 该区域 **无任何 feature**（草、花、树全部消失）；
- 即便它侥幸留下，`featuresPerStep.get(step)` 里也没有它的 `PlacedFeature`（因为 `buildFeaturesPerStep` 的输入是 `List.copyOf(possibleBiomes())`）→ 偏移 `494-506` 取 `StepFeatureData` 时它的 feature 列表为空。

**两条独立路径都指向同一结论：新群系必须进入 `biomeSource.possibleBiomes()`。**

> ⚠️ **同时修正一处历史记录的错因定位**：
> `golden-erdtree-sanctuary/src/main/java/local/plaincraft/erdtreesanctuary/mixin/BiomeSourceMixin.java:26-31` 的注释称
> 「`NoiseBasedChunkGenerator#buildSurface` 会调用 `biomeSource.possibleBiomes()` 并对其结果做 `retainAll`」。

> 真正做 `retainAll` 的是 **`ChunkGenerator#applyBiomeDecoration`**。
> 现象（"地形正常但特征阶段全跳过"）与该注释描述一致，但**归因对象错了**——正确的归因恰好落在本报告推荐的注入点上，这对长城反而是好消息：**约束与注入点在同一方法内，可一并处理。**

### 3.5 边界效应（诚实标注）

`BiomeManager.getBiome` 会先把坐标减 2 再右移 2：

```

4: iconst_2 ; 5: isub
7: aload_1
8: invokevirtual BlockPos.getY:()I
11: iconst_2 ; 12: isub
...
22: iload_2 ; 23: iconst_2 ; 24: ishr → quartX
```

对区块 `k` 的最左两列 `x = 16k` 与 `16k+1`：`(16k-2)>>2 = 4k-1`，`(16k+1-2)>>2 = 4k-1`
⇒ quart 落在区块 `k-1` ⇒ 8 角点覆盖 `k-1` 与 `k` 两个区块，最近邻可能选中 `k-1`。

- 影响面：**只有 -X 与 -Z 方向各 2 格宽的边缘**（`x ∈ {16k, 16k+1}`，`z` 同理）。`x ≥ 16k+2` 时必落在本区块。
- 后果：若只覆写中心区块、不覆写 `k-1` 邻居，则边缘 2 格上的树木 `BiomeFilter` 可能读到邻居的旧群系而拒绝放置（树被"吃掉"），或反之。
- **设计建议**：把群系覆写做成**纯世界坐标函数**（而非依赖区块当前状态），这样无论区块处理顺序如何、邻居数组是否已被同规则覆写，结果都自洽。金圣域的 `SanctuaryBiomeWriter` 正是这个形态（由 `context.biomeAt(blockX, blockZ)` 按坐标算）。
- **未验证**：该 2 格边界效应在真实运行中的实际可见程度（需要实机/gametest 统计边缘列树木数量），本报告只给出字节码推导。

### 5.3 🔴 但它真正生效，靠的是第二个 mixin

`BiomeSourceMixin.java:42-52`：

```java

    if (!((Object)this instanceof MultiNoiseBiomeSource)) return;
    if (!SanctuaryRuntime.isOverworldSource((BiomeSource) (Object) this)) return;
    Set<Holder<Biome>> sanctuary = SanctuaryRuntime.biomes();
    if (sanctuary.isEmpty()) return;
    Set<Holder<Biome>> biomes = new LinkedHashSet<>(callback.getReturnValue());
    biomes.addAll(sanctuary);                       // ★ 把圣域群系加进 possibleBiomes
    callback.setReturnValue(Set.copyOf(biomes));

```

结合 §3.4：**没有这个 mixin，`retainAll` 会把圣域群系删掉，`applyBiomeDecoration` 一个 feature 都不会派发。**
所以金圣域是「**写数组 + 改 possibleBiomes**」的**组合方案**，两部分都不可省。

`MultiNoiseBiomeSourceMixin.java:27-36`（注入 `getNoiseBiome` HEAD）解决的是**另一个**问题：
让 BIOMES 阶段（以及 NOISE/SURFACE/CARVERS 时读 `BiomeSource` 的路径，如 `buildSurface` 的 `BiomeManager` 缓存填充）
在采样时就得到圣域群系——但**对 FEATURES 的 feature 派发不是必需的**（派发读数组）。
它对本报告第 3 题的意义：**属于"锦上添花/前置一致性"，不是"树木服从"的必要条件**。

## 6. 有没有更早/更晚的注入点？各自影响范围

| 注入点 | 阶段 | 覆写数组后是否传播到树木派发 | 影响范围 / 代价 |
|---|---|---|---|
| `NoiseBasedChunkGenerator.doCreateBiomes` HEAD/TAIL | BIOMES (3) | ✅ 会（下游全部读数组） | **最早**。但此刻**地形高度尚未确定**，无法按最终地表决定群系；且 `createBiomes` 跑在 `Util.backgroundExecutor()`（`CompletableFuture.supplyAsync`），线程约束需另行评估。**改群系还会改 aquifer 的水/岩浆判定**（NOISE 阶段读 biome）。 |
| `ChunkGenerator.createBiomes` HEAD/TAIL | BIOMES (3) | ✅ 会 | 同上；且它是**抽象方法**，TAIL 注入对 `NoiseBasedChunkGenerator` 与 `DebugLevelGenerator` 都生效——覆盖面比预期大。 |
| `NoiseBasedChunkGenerator.fillFromNoise` / `generateNoise` | NOISE (4) | ✅ 会 | 太早且影响流体/含水层语义（`Aquifer.FluidPicker`）。不推荐。 |
| `NoiseBasedChunkGenerator.buildSurface` HEAD | SURFACE (5) | ✅ 会 | **金圣域正是用它改地形**（`NoiseBasedChunkGeneratorMixin.java:21-23`）。在此改群系会**同时**改地表材质规则（`SurfaceSystem` 经 `BiomeManager` 读数组）与下游 feature。但 SURFACE 不能保证覆盖所有路径（例如 `isUpgrading` 的区块、老区块升级走的是 `LOADING_PYRAMID`），存在漏网。 |
| `ChunkGenerator.applyCarvers` / `NoiseBasedChunkGenerator.applyCarvers` HEAD | CARVERS (6) | ✅ 会 | 会改 `carverBiome` 的雕刻器配置；且并非所有 generator settings 都会跑 carvers。 |
| **`ChunkGenerator.applyBiomeDecoration` HEAD** | **FEATURES (7)** | ✅ 会 | **推荐**（见 §7）。位置最晚、最贴近派发点；此时地形/地表/雕刻已全部完成，群系判定可用最终地表数据；且半径 0/1 的邻居已保证到 CARVERS，其数组可安全读。**唯一代价**：区块已 `hasAnyStructureReferences()` 等结构信息已定，但这不影响群系。 |
| `ChunkGenerator.applyBiomeDecoration` TAIL | FEATURES (7) | ❌ **不会** | 派发已经做完；只能用于"事后装饰"（金圣域用它做 `SanctuaryFinalDecorator`）。**对树木无效**。 |
| `ChunkMap.applyStep` 包装（如 `VanillaGateMixin`） | 任意 step 边界 | ⚠️ 取决于时点 | 长城已有 `VanillaGateMixin` 包装 `applyStep`（`src/main/java/local/plaincraft/greatwall/mixin/VanillaGateMixin.java:20-73`）。**注意**：它是在 `original.call(...)` **之前**插入逻辑，即在 step **任务执行前**。若在 `step.targetStatus() == ChunkStatus.FEATURES` 的分支里写群系数组，**等价于在 `applyBiomeDecoration` 之前**，效果与 HEAD 注入一致，而且**不需要新增 `ChunkGenerator` mixin**——这是与现有架构最贴合的一个备选落点。**未验证**：该路径与 C2ME 兼容层的交互（`services.productionFixture()` 分支与非 production 分支是两条不同代码路径，见 `VanillaGateMixin.java:33-56` 与 `:57-72`），需要在两条路径上都验证。 |

> 说明：**没有任何注入点能改变"是否在 FEATURES 之前写群系"这一根本事实**——
> 因为群系本来就写在 FEATURES 之前；问题是 FEATURES 时读到的是**原版采样的结果**，
> 所以任何在 FEATURES 派发**之前**完成的覆写都是有效的，越晚越贴近真实地表、越安全。

## 7. 推荐注入点 + 理由

### 7.1 推荐：`ChunkGenerator.applyBiomeDecoration` 的 `@At("HEAD")`

**理由（按重要性排序）**

1. **它就是数据的读取点，是唯一的"最后机会"**。
   派发集合在偏移 141-158 才从 `getSections()[i].getBiomes()` 构建；
   HEAD 注入保证"写"严格早于"读"，且写入的是**同一个对象**（`LevelChunkSection.fillBiomesFromNoise` 会 `putfield` 替换容器，见 §5.2）。
2. **它与 `retainAll` 约束同处一个方法**（偏移 163-177）。
   由于 R3 禁止改 `possibleBiomes()`，必须在这里就能判断"新群系是否在 `possibleBiomes()` 中"，
   并据此选择降级策略（见 §7.3）。把注入点放在别处会让这个判断分散到两个阶段。
3. **此时所有地形相关阶段已完成**（NOISE/SURFACE/CARVERS 均在下标 4/5/6）。
   群系判定可以安全依赖**最终地表高度**（长城已有 T0 / `SurfaceProbe` / `WallStageCoordinator` 体系），
   不会像 `createBiomes`(BIOMES) 那样"还不知道地面在哪"。
4. **半径 0/1 的邻居必已到 CARVERS**（`addRequirement(CARVERS, 1)`，见 §1.2），
   因此读邻居数组是安全的，不会触发 `IllegalStateException`。
5. **不与长城现有 red line 冲突**：
   该位置不改 `possibleBiomes()`、不同步 `getChunk`（`applyBiomeDecoration` 内部自己会调，属于原版行为，不是长城新增调用）、不 `join/get` future。
6. **金圣域已在生产验证过这个时点**（`ChunkGeneratorMixin.java:25`），风险已知。

**备选（与现有架构更贴合）**：在既有 `VanillaGateMixin`（`src/main/java/local/plaincraft/greatwall/mixin/VanillaGateMixin.java:20`）的
`step.targetStatus() == ChunkStatus.FEATURES` 分支里、`original.call(...)` **之前**写入群系数组。
优点是不新增 `ChunkGenerator` mixin、复用长城已有的 mailbox/lease 调度；缺点是 `applyStep` 是 step 边界，
语义不如 `applyBiomeDecoration` HEAD 直白，且需在 `productionFixture()` 与非 production 两条分支上分别验证（标记**未验证**）。

### 7.2 必须同时满足的前提（否则方案无效）

> **「万里长城群系」必须是 `biomeSource.possibleBiomes()` 的成员。**

否则 `applyBiomeDecoration` 偏移 163-177 的 `retainAll` 会把它删掉，
且 `ChunkGenerator` 构造器构建的 `featuresPerStep`（输入为 `List.copyOf(possibleBiomes())`）里也没有它的 feature
⇒ 被覆写区域**零 feature 派发**（草、花、树全没）。

### 7.3 三条可选路径（需要用户裁定，因为涉及 R3）

| 方案 | 做法 | R3 合规性 | 代价 / 风险 |
|---|---|---|---|
| **A. 复用原版群系**（推荐用于"只关心树/材质"的场景） | 覆写数组时写入**已在 `possibleBiomes()` 中**的某个原版群系（如 `minecraft:taiga`）。不创建新群系。 | ✅ **完全不碰 R3** | 拿不到独立的"长城群系"身份（无独立群系 ID、无独立雾效/音乐/刷怪表）。但**树木会立刻服从**（taiga 的 feature 表生效），且 `BiomeFilter` 通过。 |
| **B. 新群系 + 不改 `possibleBiomes`** | 建 `plaincraft_great_wall:*` 群系 JSON，写入数组。 | ✅ 形式上不碰 R3 | **群系会被 `retainAll` 删除 ⇒ 该区块不派发任何 feature。** 此时必须**自己接管装饰**（长城已有 `ChunkWallWriter` / `ProductionWallPipeline` 直接写方块，也有 `TreeFeatureMixin` 做抑制）——即"新群系只作视觉/材料标识，植被由长城自己写"。这是**可行但语义不同**的路径。 |
| **C. 新群系 + 注入 `possibleBiomes`** | 复刻金圣域 `BiomeSourceMixin`。 | ❌ **直接违反 R3**，且 `S1-城墙本体.md:1523` 明文拒绝复制该 mixin | 需要**用户显式授权**。且必须做维度白名单隔离（金圣域 0.7.13 的教训，`BiomeSourceMixin.java:18-38`）。 |
| **D. 数据包覆盖气象参数表** | 用数据包覆盖 `data/minecraft/worldgen/multi_noise_biome_source_parameter_list/overworld.json`，把新群系加进 `parameters`。这样 `MultiNoiseBiomeSource.collectPossibleBiomes()` 天然包含它，`possibleBiomes()` 无需被修改。 | ✅ 不改方法 | **未验证**。已知风险：(1) 该 JSON 是整体替换而非合并，会**clobber 其它 mod 对主世界预设的追加**；(2) 任何进入 parameters 的群系都可能被 nearest-neighbor 采样到 ⇒ **新群系会在世界上某处自然生成**，需靠极端参数点规避，但 multi_noise 是最近邻，**是否真能完全规避未验证**；(3) 版本升级时该表内容会变，维护成本高。 |

> **需要用户决定的是**：目标是 **(a)「城墙上不长树」**、**(b)「城墙区域使用某套树/植被」**、还是 **(c)「需要独立的群系身份（雾效/音乐/刷怪/材料）」**？
> - (a) **不需要任何群系改动**：长城现有 `TreeFeatureMixin`（`src/main/java/local/plaincraft/greatwall/mixin/TreeFeatureMixin.java:15-33`）已经在 `TreeFeature.place` 的 HEAD 按 `VegetationGuard` 走廊快照取消越界树，且注释明确区分了骨粉路径（`context.level() instanceof WorldGenRegion`）。这条路已在架构建成。
> - (b) 走 **方案 A**（复用原版群系）即可，零 R3 风险。
> - (c) 必须在 **C**（授权破 R3）与 **D**（未验证的数据包路径）之间选择。

### 7.4 若采纳方案 A/B 的落地细节

1. **覆写要做成纯世界坐标函数**（见 §3.5），保证与你无关的区块处理顺序不能改变结果。
2. **覆写范围建议覆盖中心区块 + 其 `k-1` 邻居**（或干脆与 `ProtectionSnapshot.leaseRadiusChunks()` 同口径），
   以消除 §3.5 的 2 格边界效应。注意 `FEATURES` step 的 `blockStateWriteRadius(1)`，
   以及长城现有 lease 上界 81 区块（`FeaturesLease.java:29`、`ProtectionSnapshot.java:83-93`）。
3. **写完必须 `chunk.setUnsaved(true)`**（金圣域 `SanctuaryBiomeWriter.java:56` 已这么做），
   否则覆写可能不落盘，导致"生成时是 A、存档后读出来是 B"的不一致。
4. **与长城 T0/CAPTURE 的顺序**：CAPTURE 读的是 `getPersistedStatus().isOrAfter(ChunkStatus.FEATURES)`
   的区块（`TerrainSnapshotService.java:70`），也就是 **FEATURES 任务跑完之后**的区块。
   而群系覆写在 FEATURES **任务内**（`applyBiomeDecoration` HEAD）发生，
   **因此群系覆写不会影响 T0 地形证据**（T0 只取方块状态，与群系无关；`WallStageCoordinator.capture` 只遍历 `chunk.getBlockState`）。
   两者无冲突。 ✅
5. **不要在 `applyBiomeDecoration` 的 `TAIL` 做群系覆写**：派发已完成，对树无效（§6）。
