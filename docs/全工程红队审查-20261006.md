## 结论摘要

当前不能发布，也不能签收 S1C、S2、S3、S4 或 S5。最紧急的阻断项不是测试数量，而是以下实现仍与规格不符：

1. `HistoryJournal` 的生产根目录接线使它读取错误的 manifest 路径，并且关闭接口不等待真正的 WAL force/文件关闭完成。
2. 新 Gate 的 `propose` 后以旧 revision 调 `freeze`，首次新门闸在常见 `topologyRevision=0` 情况下会确定性 revision mismatch。
3. `WallArchBackfill` 当前生成空 voxel 写集，却在准备阶段对受影响 chunk 写 ACK；这不是可验收的 durable backfill。
4. `GarrisonController` 同时要求玩家距离大于 500 格和在 24..64 格内，刷怪条件不可达。
5. `rejectUncertifiedProfiles()` 为空实现，违反规格对未认证 Tan's Huge Trees 的生产 fail-closed 要求。

已确认的保护风险包括 TreeBounds 对第三方树配置 fail-open、遗漏两个可嵌套树配置类型、黄金树反射失败静默绕过、campfire 归属检查未核对 durable proof，以及拱门回填空写/提前 ACK。

## 阻断项

### B1. HistoryJournal 使用了错误的生产根目录

| 字段 | 内容 |
|---|---|
| 问题 | 生产传给 journal 的根是 `greatwall/history`，但 journal 把它当成 `greatwall` 使用。 |
| 位置 | `src/main/java/local/plaincraft/greatwall/lifecycle/ProductionSession.java:117`；`src/main/java/local/plaincraft/greatwall/persistence/HistoryJournal.java:85-129` |
| 证据 | 生产构造为 `new HistoryJournal(root.resolve("history"), recipe.instance(), historyIo)`；随后 `readManifest()` 使用 `root.resolve("manifest")`，所以实际读取 `greatwall/history/manifest/creation.json`。同类 `HistoryCodec.path(root, "history/...")` 又会将 WAL 写到 `greatwall/history/history/...`。 |
| 影响 | 永久历史恢复可能找不到生产 manifest，或把历史文件放入错误的二级目录；重开/恢复直接阻断。 |
| 验证状态 | 仅静态推断；未用真实重启复现。 |
| 最小修复建议 | 统一 `ProductionSession` 传入的 journal root 与 `HistoryJournal` 内部路径约定，随后用新隔离世界执行创建、关闭、重开、损坏拒绝和同 JVM `A→B→A`。不迁移旧永久 T0/manifest。 |

### B2. HistoryJournal.close() 不等待关闭任务完成

| 字段 | 内容 |
|---|---|
| 问题 | `close()` 只把 force/关闭操作排入 journal 自己的队列，返回类型却是 `void`；生产随后立即完成 `drained`。 |
| 位置 | `HistoryJournal.java:536-548`；`ProductionSession.java:358-364` |
| 证据 | `HistoryJournal.close()` 通过 `admit(new Task<>(...))` 异步执行 `hooks.force(wal)`、`releaseChannels()` 和 `ioOwner.shutdown()`，没有向调用者返回完成 stage。`ProductionSession.close()` 中 `if (journal != null) journal.close(); io.shutdown(); ... drained.complete(null)` 紧接着执行。 |
| 影响 | 关闭/重启可能在 WAL force 或 channel close 完成前被报告为 drained，造成尾写丢失、文件锁竞争或下一 session 读到未完成状态。 |
| 验证状态 | 仅静态推断；`S1C-DRAIN-01` 继续 OPEN。 |
| 最小修复建议 | 让 journal 暴露可等待的 close/drain stage，并让 ProductionSession 只在 journal stage、bootstrap stage 和自身 IO 都完成后发布 `drained`；关闭异常不得被吞掉。 |

### B3. 新 Gate freeze 使用旧 expectedRevision

| 字段 | 内容 |
|---|---|
| 问题 | `propose()` 生成 revision `current revision + 1`，但 `NegotiatedGateService` 仍用请求的旧 revision 调 `freeze()`。 |
| 位置 | `src/main/java/local/plaincraft/greatwall/compat/road/NegotiatedGateService.java:391-397`；`src/main/java/local/plaincraft/greatwall/persistence/GateLedger.java:39-95` |
| 证据 | 调用链为 `ledger.propose(..., request.topologyRevision()).thenCompose(proposed -> ledger.freeze(proposed.contract().id(), request.topologyRevision()))`。`GateLedger.propose()` 在 `GateLedger.java:67` 写入 `revision + 1L`；`freeze()` 在 `:79-81` 要求 `current.revision() == expectedRevision`。 |
| 影响 | 首次新 gate 且请求 `topologyRevision=0` 时，proposal 已是 revision 1，freeze 仍期待 0，事务失败，S2/S5 门闸协商不能完成。 |

| 最小修复建议 | 由已提交的 proposal record 携带并传递 freeze 所需的 revision；不要重新从 request 推导。增加首次新 gate、重复请求、并发 proposal 和恢复后继续 freeze 的测试。 |

| 字段 | 内容 |

## 中风险

### M1. gameplay 尚未 ready 就允许 session active 路径继续

`ProductionSession.java:117-151` 中，`journal.open().thenAcceptAsync(...)` 一开始即调用 `active()`（`:120`），此时 BeaconLedger、GateLedger、WallWorldState、NegotiatedGateService 等对象尚未构造，直到 `:121-148` 才完成 gameplay assembly。`active()`（`:298-300`）只检查 closed/failed，并不检查 `PRODUCTION_GAMEPLAY_READY`。这会让外部调用在历史恢复完成但 gameplay 尚未发布时通过基础 session gate。仅静态推断；最小修复是引入显式 `PENDING/READY/FAILED/CLOSED` 状态并让所有 gameplay API 只接受 READY。

### M2. WAL replay 后 BeaconLedger 可能使用旧 beacon count

`HistoryJournal.openOnOwner()` 在 `:110` 先从 HEAD 设置 `beaconCount`，随后 `readWal()` 回调在 `:113-118` 对 beacon record 增加内部 `beaconCount`；但 `ProductionSession.java:121-124` 用的是 `recovery.head().beaconCount()`，即 replay 前的 HEAD 值。若 WAL 含尚未 checkpoint 的 beacon 事件，新的 `BeaconLedger` 可能落后于已验证日志。仅静态推断；需用 WAL 尾记录重开测试确认。最小修复是让 recovery 返回 replay 后的派生 state，并由 `WallWorldState`/BeaconLedger 共同核对。

### M3. RoadWeaver adapter 的 pending/cleanup/双向调用链未闭合

`RoadAdapterState.java:145-158` 在 proposal 后明确抛出 `profilePending(record)`；`RoadAdapterState.java:207-223` 的副作用继续依赖 `port.whenReady()`，同时 `RoadWeaverAdapter.java:102-130` 才在 live bind 后注册 provider。commit `621a924` 修正了 provider 注册时机方向，但没有证明 session ready、STOPPING/UNLOAD 注销、同 JVM `A→B→A`、双向真实规划和 durable profile/BEGIN 已闭合。影响是 RoadWeaver 可能看到 provider 但 session pending/closed，或请求永远挂起/失败。仅静态推断，S2 不得签收。

### M4. TorchIgnitionMixin 在客户端可能把 null server 传给 ConcurrentHashMap

`src/main/java/local/plaincraft/greatwall/mixin/TorchIgnitionMixin.java:22-32` 直接调用 `WorldServices.find(context.getLevel().getServer())`。客户端 level 的 `getServer()` 可能为 null，而 `ConcurrentHashMap.get(null)` 会抛 `NullPointerException`。规格要求客户端不造服务、专用服务器不加载客户端类，但该实现没有先判断 null。仅静态推断；需要实际客户端 smoke。最小修复是在查找前显式判断 client/server，或提供接受 level 的安全查询入口。

### M5. BudgetCache 的取消 waiter 没有从 single-flight callers 清理

`src/main/java/local/plaincraft/greatwall/diagnostics/BudgetCache.java:85-96` 将重复请求加入 `Loading.callers`；完成路径 `:122-139` 遍历整个 callers 分发结果。当前取消 lease/future 的路径只完成或失效调用者，没有把已取消 caller 从 callers 移除。长期阻塞的 single-flight 请求会积累无效 waiter。仅静态推断；最小修复是为 caller 建立取消回调并在 owner 线程从 callers 移除，同时保留 loading 的正确生命周期。

### M6. DiagnosticExporter 在规划 future 上调用 join

`src/main/java/local/plaincraft/greatwall/command/DiagnosticExporter.java:130-145` 在 `requireWindow()` 中调用 `lease.future().join()`。它可能运行在 IO/命令路径而非世界生成线程，当前不能直接认定违反 worldgen 线程红线；但若从 worldgen owner 调用，会阻塞线程并绕过显式异步合同。验证状态为仅静态推断。最小修复是将 exporter 设计为返回 completion stage，或在调用边界明确只允许非 worldgen 线程。

### M7. repair confirm 是带成功语义的零写接口

`src/main/java/local/plaincraft/greatwall/command/GreatWallCommands.java:616-633` 在校验 token、fixture 后直接返回 `repair confirm ... token validated, zero writes (backfill not wired in this session)`，没有执行 backfill，也没有完整 gate/session/proof/revision 验证。源码行为已确认，影响是运维或自动化调用者可能把“confirm 返回 1”误当作修复完成。最小修复是未接线时返回明确失败/未实现，不把 token 验证当作 repair 成功；接线后必须等待 durable backfill 结果。

### M8. S5 Gradle 任务是假入口

`gradle/production-tests.gradle:58-67` 中 `runS5Faults` 和 `runS5Stress` 都只 `dependsOn runServerSmoke`。普通 smoke 不等价于规格要求的 18 fault points、exception/halt、10 rounds 或 24h stress。仅静态推断；最小修复是任务分别绑定实际 fault/stress runner，并让报告逐项记录，而不是复用一个普通 smoke 退出码。

### M9. NativeSchedulerFixture 的性能观测判断恒真

`src/serverSmoke/java/local/plaincraft/greatwall/smoke/NativeSchedulerFixture.java:61-67` 使用 `d.getOrDefault("max-batch-nanos", 0L) >= 0L`。缺字段时默认 0，任何非负 long 都为 true，所以 `BLOCKED_PERFORMANCE` 分支实际上不会触发。这个问题独立于用户授权移除 40ms 硬拒绝；不建议恢复硬 gate。最小修复是判断字段存在且值有效，继续只记录慢批次。该 bug 是静态可证，未在真实 smoke 中验证输出。

### M10. RoadWeaver 兼容文档与运行时 allowlist 不一致

`docs/release/compatibility.json:31-36` 声明 RoadWeaver `.405`，SHA 为 `2ecf57...`；`src/main/resources/plaincraft_great_wall/roadweaver-interop.sha256:1-8` 只允许另一个 SHA `bed132...`，对应 `.406` 的归档指纹。运行时 allowlist 可作为 ABI 安全闸，但发布文档必须与实际可启动 artifact 一致。已静态实测文件不一致；最小修复是重新审查实际 jar、更新文档或 allowlist 中正确的一方，不能只改文字绕过校验。
