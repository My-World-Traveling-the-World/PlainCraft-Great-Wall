## 一、先说结论（大白话）

你要做的事情可以概括成三句话：

1. **算一条线** —— 长城要走哪（这个已经有代码，约 8.7 分钟）
2. **沿着线贴标签** —— 告诉游戏「这条线两侧是长城群系」
3. **标签说「这里不长树，只长我指定的矮树」** —— 游戏就照做

**关键好消息**：贴标签这件事，**你的整合包里已经有一个 mod 专门干这个**（Lithostitched），而且**用它的公开 API 就行，不用碰长城那条红线**。

## 二、为什么之前的方案要破红线，现在不用了

### 2.1 之前的困境

圣域（黄金树）用的手法是：**直接改 `possibleBiomes()` 方法**。

而长城有条铁律（R3）：**绝不碰 `possibleBiomes()`**。

所以要么破例，要么方案作废。

### 2.2 转机：Lithostitched 提供了官方入口

我核实了 Lithostitched 的 API（`lithostitched-1.8.0+beta6`，**你的整合包里确实装了**）：

```java
// Lithostitched 官方 API
public interface BiomeInjector {
    List<Holder<Biome>> possibleBiomes();     // ← 这就是"往群系表里加东西"的官方入口
    ...
}
public interface AddBiomeInjectorsEvent {
    void addInjectors(..., BiConsumer<ResourceLocation, BiomeInjector>);
}
```

**含义**：
- `possibleBiomes()` 是 Lithostitched **自己**在它内部调用的
- 我们只是**给它提供数据**（告诉它"把这个群系加进去"）
- **我们自己的代码一行都不碰 `possibleBiomes`** → **不违反红线**

### 2.3 真实范例（我提取的）

`Terralith` 这个 mod 就是这么做的。它的数据包里有：

```
disable.skylands/data/terralith/lithostitched/biome_injector/disable_skylands_autumn.json
```

内容（**完整范例，11 行**）：
```json
{
  "type": "lithostitched:replace_fully",
  "dimension": "minecraft:overworld",
  "targets": "terralith:skylands_autumn",
  "replacement": "minecraft:deep_ocean"
}
```

**路径规律**：`data/<你的命名空间>/lithostitched/biome_injector/<任意名字>.json`

**这意味着**：长城只要往这个目录放 JSON 文件，就能注册群系。**纯数据，不用写 Java。**

## 三、Lithostitched 全部 5 种注入类型（我 javap 提取的）

| type | 作用 | 字段 |
|---|---|---|
| `lithostitched:add_points` | **往气候参数表加点**（新群系会在特定气候生成） | `biome`, `points` |
| `lithostitched:dispatch_alternate_layout` | 分发备用布局 | `biome`, `points` |
| `lithostitched:force_placement` | **强制某群系在指定参数处生成** | `biome`(+-参数) |
| `lithostitched:replace_fully` | **完全替换某群系** | `targets`, `replacement` |
| `lithostitched:replace_partially` | 部分替换 | `targets`, `replacement` |

**对长城有用的**：
- 如果只想"让群系存在"→ 用 `add_points` 或 `force_placement`
- 但**长城的用法更特殊**（见第四节）

## 四、长城的实际做法（和 Terralith 不一样）

**关键差异**：Terralith 是**让群系按气候自然生成**；长城是**按算出来的路线精确覆盖**。

所以长城要**两条腿走路**：

| 步骤 | 手法 | 作用 |
|---|---|---|
| **① 让群系"存在"** | `data/plaincraft_great_wall/lithostitched/biome_injector/*.json` | 让游戏知道有这个群系（进 `possibleBiomes`） |
| **② 按路线精确覆盖** | 抄圣域的 `SanctuaryBiomeWriter`（写 chunk 群系数组） | 在长城路线经过的地方贴标签 |

**为什么两条都要**（这是子智能体挖出的关键机制，我复核过）：

```java
// ChunkGenerator.applyBiomeDecoration 字节码，偏移 163-172
biomeSet.retainAll(biomeSource.possibleBiomes());
```

游戏在长树前会做一次「求交集」：
- **只做②不做①** → 群系被 `retainAll` 删掉 → **该区块连草花矿石都不生成**（不是"不长树"，是"什么都不长"）
- **只做①不做②** → 群系只按气候自然生成，**不会精确落在长城路线上**

**所以①+②缺一不可。而①是靠数据包（不碰红线），②是抄圣域（也不碰红线）。**

## 七、必须知道的 4 个坑

### 坑 1：Lithostitched 下的群系注入是"包装器"，不是原版 MNBS

我 javap 实证：
```
InjectorBiomeSource extends net.minecraft.class_1966   ← = BiomeSource，不是 MultiNoiseBiomeSource
BiomeInjectorManager.applyBiomeInjectors 偏移 474: setBiomeSource(...)  ← 整体替换
```

**后果**：
- 圣域那两个 mixin 在你的整合包里**双双失效**（instanceof 判断不过 + Mixin 目标类不匹配）
- **这解释了为什么圣域在你的整合包里群系可能一直没真正生效**
- **但对我们有利**：说明「写 chunk 数组」这条路（`SanctuaryBiomeWriter`）才是真正起作用的

### 坑 2：`retainAll` 会把不在表里的群系删干净

见第四节。**必须同时做①和②。**

### 坑 3：新群系默认材质是 STONE

`BiomePaletteIndex.classify`（`decay/BiomePaletteIndex.java:82-91`）兜底返回 `STONE`。
**不写 palette tag → 静默用石头材质**（看起来没坏，实际用错）。

### 坑 4：加 worldgen 文件会让旧存档失效

`GenerationResourceFingerprint` 会把 `worldgen/` 算进世界指纹 → 哈希变 → `WORLD_RECIPE_MISMATCH`。

**你说不考虑旧存档** —— 那这条不是问题，但要知道**必须开新世界**。

## 八、关于「预热放道路后面 + 进世界前完成」

我核实了**道路和河流的做法**（它们都阻塞进世界）：

```java
// 河流：StreamsServerLifecycleMixin.java:25-38
@Inject(method = "createLevels", at = @At(value="INVOKE",
        target="...setInitialSpawn(...)", shift = At.Shift.BEFORE))
private void prewarmStreamsBeforeInitialSpawn(...) {
    StreamsPrewarmService.beginStartup(level, x, z);
    StreamsPrewarmService.awaitStartup(level);     // ← 阻塞等待
}

// 道路：InitialGenManager.blockUntilDone(level)   在 prepareLevels 里调
```

**所以「把长城预热也放进这个阻塞链」技术上完全可行** —— 照抄它们的模式即可。

### 但你不需要整条长城都预热

长城本来就是**按段懒算**的设计：

```java
// PlannerScheduler.java:218 —— 只预热前 4 段！
for (long i = 0; i < 4 && safeSegment(i); i++) prewarm.add(requirePlan(i, Priority.PLAYER_PREFETCH));

// PlannerScheduler.java:244-245 —— 剩余段用最低优先级后台算
backgroundLease = requirePlan(background++, Priority.BACKGROUND);
```

**这正是你说的**：
- 开局预热前 4 段（约 8192 格，你说够用）
- 游玩时最低档位慢慢算

优先级五档（`WallTypes.java:42`）：
```java
enum Priority { PLAYER, ROAD, CHUNKY, PLAYER_PREFETCH, BACKGROUND }
```
`BACKGROUND` = 最低档。

## 九、一个真瓶颈：只有 2 条 lane

8.7 分钟的 `RootSearch` 慢，**不是因为预热，是因为并行度只有 2**：

```java
// WorldBootstrap.java:207-208 —— 硬编码 2 条
return List.of(new OracleLane(..., 0, ...), new OracleLane(..., 1, ...));

// OracleLane.java:36 —— 明确拒绝更多
if (index < 0 || index > 1) throw new IllegalArgumentException("oracle lane index 0..1");
```

**你的机器 16 核，只用了 2 核。**

| 优化 | 做法 | 预期 |
|---|---|---|
| **加 lane** | 2 → 8 或 16（按核数自适应） | 8.7 分钟 → **1~2 分钟** |
| 预热放开预算 | 改 `credits`/`deadline` | 效果有限（受 lane 数限制） |

**「开局启动全部硬件性能」的正解就是加 lane。**

## 十二、一句话总结

**能做，而且路径比预想干净**：Lithostitched 提供了官方群系注入 API（数据包 JSON，不碰红线），圣域的 `SanctuaryBiomeWriter` 提供了按位置精确覆写的手法（也不碰红线），树木用原版（不用自己写）。

**唯一真正的瓶颈是并行度（只用了 2 核）**，加 lane 能把 8.7 分钟压到 1~2 分钟。

**你之前担心的「要不要破 `possibleBiomes` 红线」——不需要了。**
