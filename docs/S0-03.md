## 2. 时序与重放合同

1. PREPARE 读取实际 FEATURES 写半径，保留有限 halo 的 FEATURES futures；请求不升级为 FULL，不等待别的 APPLY。
2. 锁外等待 halo FEATURES 完成，再由原生授权上下文 CAPTURE。锁内无 future 等待、磁盘 IO 或同步 getChunk。
3. T0 以 owner/配方为输入 single-flight 发布；晚到 cell 复用同一不可变 tile，不重新扫描已经放过金块的窗口。
4. T0 存证 durable 完成才允许首次 APPLY。APPLY 只写 owner，先检查完整写集的前态与保护条件；跨 chunk 实验逐 owner 重放，没有跨 owner setBlock。
5. 原生 T0/APPLIED marker 保留到晋升、序列化和恢复。已施工 owner 不重复施工；已落盘 T0 而 chunk 输出未保留时，以同一证据和前态检查恢复，不把当前墙体当自然输入。
6. 证据缺失/损坏时，依赖该 tile 的 cell 不得 APPLY；不能静默重建证据。异常传播到已认证的必需依赖失败通道，会话停止并清理等待项。

本机 C2ME 锁范围、WORLDGEN token 和 scheduler enqueue 已从实际 JAR 的运行变换类复核，导出在 `evidence/s0-03/adapter/`。也读取了工作区 QoS 的 `RuntimeLimiter` 和 `FeatureOrderCycleFallback` 源码，没有以旧 0.3 系列 C2ME 源树冒充实际 0.27 ABI。

## 3. 已验证结果

### 3.1 随机顺序与固定并发

每档新建同 seed=9282026、同配方、同坐标的隔离世界，100 个随机次序 round，每 round 四 owner。比较的是对应坐标在不同并发度下的输入/输出，**不是要求不同坐标 hash 相同**。hash 对象为 T0、实验 Realization 和整个最终 9984 状态窗口。

| 引擎 | 实际 worker 数 | 轮次 | owner 数 | 跨并发三种 hash |
| --- | --- | --- | --- | --- |
| 原版 mailbox | 1 / 2 / 8 / 16 | 每档 100 | 每档 400 | 全部一致 |
| 本机 Tectonic + C2ME CPU | 1 / 2 / 8 / 16 | 每档 100 | 每档 400 | 全部一致 |

八组全部通过，共 **800 轮、3200 owner**。每个 owner 验证 CAPTURE_EXIT < T0_DURABLE < APPLY_ENTER、原引擎 worker 上执行，以及 FULL 后的窗口 hash/marker；全部晚到请求仍读取原 T0。没有 trace 截断，等待持锁哨兵零违规，关闭后的 leases/delays=0。

最终清单：[final-matrix-results.json](evidence/s0-03/final-matrix-results.json)。不要把同目录早期单轮或未核对 worker 数的尝试算入这八组。

**固定 worker 口径**：本机 QoS 的 `workerPoolSize` 会覆盖 TOML，仅改配置不够。专用 premain agent 在类加载前只校准 `workerPoolSize`/`currentLimit` 两个容量方法，运行内核对真实 worker 数；原生区域锁不改。原版用 `max.bg.threads` 和测试专用 ActiveProcessorCount=24 解除 CPU 派生上限。此校准不改磁盘上的 C2ME JAR，不进入发布 JAR。

另保留 **原始 QoS 配置、无 agent 的 100 轮/400 owner 对照**，16 个并行实验 round，不把 16 冒充其实际动态 worker 数。结果与固定线程矩阵逐 owner 三种 hash 一致。见 [final-native-qos-results.json](evidence/s0-03/final-native-qos-results.json) 和 `adapter/checks.json`。

### 3.2 强杀、恢复与故障拒绝

原版/C2ME 各执行以下四项，共 **8/8 通过**。C2ME 使用原始 QoS，无固定线程 agent。

| 用例 | 实际动作 | 验收证据 |
| --- | --- | --- |
| durable / none | T0 已落盘、APPLY 前暂停，匹配 runId 定点强杀测试 JVM，重启 | T0_DISK_REUSED；存证文件逐字节 hash 不变；正常完成 |
| saved / none | 完成实验并执行 save-all flush 后强杀，重启 | marker/T0 复用或幂等恢复；重启前后三种 hash 相同；正常完成 |
| saved / missing | 保存、强杀、删除该隔离世界一份 T0，重启 | T0_EVIDENCE_MISSING；受影响 cell 无 APPLY、无重采；缺文件未偷偷再生 |
| saved / corrupt | 保存、强杀、损坏该隔离世界 T0 的 CRC，重启 | T0_CORRUPT；受影响 cell 无 APPLY、无重采；损坏字节未被覆盖 |

清单：[final-recovery-results.json](evidence/s0-03/final-recovery-results.json)。每个用例保存实际被终止 JVM 的身份、两次启动参数、原始日志、事件、T0 文件及关闭状态；不是模拟异常冒充进程崩溃。故障拒绝属于**预期异常退出**，不宣称正常关服或完整保存。

**测试断言纠正，失败证据保留**：`s003-recovery-tectonic-c2me-saved-corrupt-12a3a13a` 最初被“全世界 APPLY_EXIT 必须为 0”的断言拦下。实际损坏的是 2000,2000；依赖它的三个 cell 均未 APPLY，但独立的 2001,2000 先完成恢复，其三种 hash 与崩溃前完全一致。并行 DAG 不提供全世界跨 chunk 事务；不应把合法的独立恢复误判成使用坏证据施工。

现按真实 cell 依赖断言：受影响 owner 禁止进入 APPLY；全局禁止重新 CAPTURE；若健康 owner 在错误传播前完成恢复，其三种 hash 必须与原记录相同；坏文件不能重建。四个故障用例已全部重新运行。额外纯内存校验反例 **4/4**：独立健康恢复接受；受影响施工、重采、健康输出 hash 改变分别拒绝。见 `fault-verifier-tests.json`。没有修改生成实现来绕过故障。

## 5. 边界、性能与未签收内容

- 本阶段是超平坦可控 feature 屏障实验。Tectonic 已加载，不等于完成其默认地形、高度6000、黄金树/RoadWeaver 后置施工或 OpenCL 世界生成的屏障兼容验收。对应适配/真实地形验收仍属于后续工作。
- 不承诺任意第三方在 FULL 后异步改块仍无冲突；本实现仅按引擎声明 FEATURES 写半径闭合输入。
- 实验有限 100 轮；不是无限世界缓存回收、24小时堆平台、大规模 Chunky 或百万格真实城墙压力测试。
- 本机 Ryzen 7 5700X，8核16线程，约32GiB内存，Windows 11。配置与源码 hash 在 `source-environment.json`。完整锁内阶段耗时见 `adapter/stage-timings.json`。
- CAPTURE/APPLY 的墙钟最大样本约 **43.50ms**，部分档超过40ms；不隐藏，不声称所有阶段满足严格40ms上界。该数据是 worker 端原型/校验窗口操作，不是主线程规划 slice 性能认证。后续性能工作仍需处理尾延迟，不能以此报告签收 S5。
- 只验证“提交后存证在本机进程强杀中保留”，不承诺断电/损坏文件系统的完整事务语义。原子 move 不支持时直接在 APPLY 前失败，没有静默非原子覆盖兜底。
- 两次早期固定线程 Mixin 尝试因目标类在 preLaunch 已加载而失败，日志保留；改为测试 premain 校准后通过。首次泛型编译失败也保留。失败尝试不计入最终通过组。
