## 1. 阻断项

### B1. `region` 不是沿长城路线的几何区域

| 字段 | 结论 |
|---|---|
| 问题 | 草案把 Lithostitched 的区域权重系统误当成动态走廊 mask。 |
| 位置/证据 | J-3：区域由本底群系列表、权重和 region density function 决定；没有墙路线、轴、包络或多边形字段。JSON 只有 dimension/biomes/weight，record 的 `name` 是运行时 key，不是额外几何字段。 |
| 影响 | 静默失效：不沿墙出现，或在整个本底群系分布中出现；新 region 还可能改变其它 region 的权重分区。 |
| 验证状态 | 已实测：codec/字节码；具体世界效果仅静态推断。 |
| 结论/改法 | 不创建“长城几何 region”。把“注册可用群系”与“沿最终路线改 chunk 数组”分开；路线由长城自己的冻结计划提供。禁止用未 ready 时返回 false 的路线 density function 冒充确定 mask。 |

特别反例：region 的 `biomes` 若只列新长城群系，注入前本底通常不含它，不会凭空得到长城走廊。`parameters:{}` 且不指定 region 的 ForcePlacement 则匹配整维度，不符合选项 A（J-2）。

### B2. FEATURES HEAD 只覆写 owner，无法保证邻块装饰输入一致

| 字段 | 结论 |
|---|---|
| 问题 | 每块在自己的 FEATURES HEAD 改群系，不能保证它被邻块查询时已经改完；提前改又可能污染邻块地表生成。 |
| 位置/证据 | J-6 收集 3×3 所有 section；J-7 的 FEATURES 只要求邻块 CARVERS；[SanctuaryBiomeWriter.java:36](D:/云游四海-Mod源码/golden-erdtree-sanctuary/src/main/java/local/plaincraft/erdtreesanctuary/SanctuaryBiomeWriter.java:36) 只修改传入 chunk；J-8/J-9 证明 SURFACE 会通过 BiomeManager 读邻 quart。 |
| 影响 | 静默失效 / 地表变化 / 并发风险：同一输入随生成先后次序产生不同装饰；越权修改邻块可能触及别的 owner。 |
| 验证状态 | 已实测：调用链与阶段依赖；竞态仅静态推断，NOT_RUN。 |
| 结论/改法 | 不能直接复制 HEAD。需要锁外计划依赖、明确的 owner paint 时点与邻块完成屏障，同时保护 SURFACE 的本底输入。Vanilla 与 C2ME 都必须实现同一合同。 |

静态反例：A=(0,0) 已到 CARVERS 并覆写，B=(1,0) 尚在 SURFACE。B 的 x=16 附近经八角取样可选到 A 的 quartX=3。把 writer 移到“本块 CARVERS 后”仍可能改变 B 的地表。

可验证的阶段增量：

```text
锁外 route/mask ready
    → 本块 CARVERS 额外要求 SURFACE radius 1 ready
    → 原生 CARVERS
    → owner 内保存本底群系、仅覆写本块
    → paint 完成后才完成 CARVERS future
    → FEATURES 原有 CARVERS radius 1 保证 3×3 全部 painted
```

这里新增的是 CARVERS→更早 SURFACE 的有向依赖，不是相邻 CARVERS 互等。一个 FEATURES 的 3×3 CARVERS 将间接要求 5×5 SURFACE；这是额外依赖面，不是整个原生任务的全部依赖面。**必须先验证 C2ME 图、lease/capacity、取消、停止和重入；本报告不把它记为已可用。** 不允许持锁补申请、不写邻块、不等 T0/APPLY。

现有接入只覆盖 FEATURES / INITIALIZE_LIGHT：[VanillaGateMixin.java:34](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/mixin/VanillaGateMixin.java:34)、[C2meProbeAdapter.java:31](D:/云游四海-Mod源码/plaincraft-great-wall/src/main/java/local/plaincraft/greatwall/compat/c2me/C2meProbeAdapter.java:31)。所以这不是只添加一个 writer 的工作。

### B3. 一个固定群系不能保证“只改树，其余生成照旧”

| 字段 | 结论 |
|---|---|
| 问题 | 改整列群系同时改变洞穴身份、非树 features、生成设置与游戏环境，不能等同于树木开关。 |
| 位置/证据 | [SanctuaryBiomeWriter.java:42](D:/云游四海-Mod源码/golden-erdtree-sanctuary/src/main/java/local/plaincraft/erdtreesanctuary/SanctuaryBiomeWriter.java:42) 命中 XZ 后忽略 sampleQuartY；J-6 用群系 generation settings 汇总每个 step；J-10 的新 feature 排序可能成环，J-6 @624..632 的 feature 索引也进入随机种子。 |
| 影响 | 静默失效 / 崩溃：洞穴、矿石、湖泉等变化；共享 feature 排序不一致可启动失败。新增注册即使不自然选中，也不能未经验证声称原 feature 索引全不变。 |
| 验证状态 | 已实测：writer 与派发机制；新方案具体差异仅静态推断。 |
| 结论/改法 | 限定地表 quart 带，不全 Y 覆写；保存原 BIOMES 值。严格解释“只改树”时，非植被 step 及其 BiomeFilter 应使用本底 view，景观 step 用路线 view，并校验原 feature 索引/种子保持。不能把固定 plains features 当所有群系的原装饰。 |

推荐按严格需求设计 `BaseBiomeSnapshot + DecorationBiomeView`，不是暗中放宽需求。该 view 必须覆盖 native 群系集合收集、step 派发及对应 placement 查询，而不只是改一个 BiomeManager。不得为方便重写整套原版装饰器。

**step 9 也包含草花等非树装饰，不能整阶段粗暴替换。** 需要具体 feature 级政策：本底非树派发保留，原树在指定景观域内按政策抑制，自家树只在允许带派发；两者仍受同一硬保护检查。放置来源用明确的 owner-local dispatch scope 标识，不用命名空间豁免保护，不复制 ThreadLocal 到异步线程。混合树/非树或后置写入无法证明安全的 feature 必须拒绝该 profile 认证，不能把未知配置归为“已抑制”。树木自身占位造成的预期装饰差异，也应单列许可差异范围，而不是声称所有最终方块逐字节完全一样。

恢复也是前置：paint 后、FEATURES 前可保存退出；未来新邻块还会读已经生成的邻块。因此原群系不能只保存在一次任务的临时 map。需要随 affected chunk 持久化稀疏本底 biome key/版本/hash，或先证明等价的可恢复来源；不能直接把当前 source 重采样称为原 BIOMES 数组。预算、损坏拒绝和旧 reader 排空必须定义。已有 T0、before-state、负空间合同不变。

若用户只要求 NOISE/SURFACE/CARVERS 不变、允许其它装饰改为固定模板，可省掉部分 view 工作，但这是**另一个需求裁决，尚未获得授权**。

一个 biome 可以含多个景观带，但仅给两个 placed_feature 取 grove/edge 名字不产生空间约束。需 route-band PlacementModifier 或等价的明确过滤合同。

### H3. 维度与“无硬依赖”要在所有入口成立

## 4. 十二个问题逐项回答

### 1. ForcePlacement + region 是否能实现选项 A？完整格式是什么？

**单靠这两个 JSON 机制不能表达动态墙走廊**（B1 / J-3）。beta6 的实际类型是 record implementing interface；dimension key 对应 `LevelStem`，不是草案中写的 `ResourceKey<Level>`。

顶层格式：`type`、可选 `predicate`、必填 `dimension`、可选 `priority`（默认 1000）、必填 `biome`、必填 `parameters`、可选 `region`。parameters 的 key 是 climate parameter 或 density function；值可为单值或 `min_inclusive/max_inclusive` 范围。region 不放进 parameters 内。

下例是**codec 格式示例，不是长城路线方案，未加载验证**：

```json
{
  "type": "lithostitched:force_placement",
  "dimension": "minecraft:overworld",
  "priority": 1000,
  "biome": "plaincraft_great_wall:great_wall",
  "parameters": {
    "temperature": {"min_inclusive": 0.0, "max_inclusive": 1.0}
  },
  "region": "plaincraft_great_wall:great_wall"
}
```

**建议注册-only 候选**：density function 恒为 0，ForcePlacement 要求它为 1，所以只注册身份、不在 source 自然采样中选出该群系：

```json
{
  "type": "lithostitched:force_placement",
  "dimension": "minecraft:overworld",
  "priority": 1000,
  "biome": "plaincraft_great_wall:great_wall",
  "parameters": {
    "plaincraft_great_wall:registration_zero": 1.0
  }
}
```

对应 `worldgen/density_function/registration_zero.json`：

```json
{"type": "minecraft:constant", "argument": 0.0}
```

依据 J-1/J-2/J-4/J-11，这个候选具有所需机制；**真实 RegistryOps 解码、optimizer 适配与跨 seed 不匹配均 NOT_RUN，不能当已经验证的 datapack 使用**。不要用 `predicate:false`，那可能连整个 injector 都不加载。先验证这两个最小资源，再铺其它文件；若失败，停止此候选，不去修改 R3 接口。

### 2. InjectorBiomeSource 是否把 injector 群系计入集合？

**会**，见 J-4 @58..73、@0..35 与 J-1 @0..7。加入集合不要求该 ForcePlacement 当前 matches=true。因此注册-only 的机制有依据。

但之后还有 fully-replaced 过滤，规则未加载或被其它规则替换仍可能排除身份。必须在实际资源组合中检查；不能把纯字节码肯定句扩大成整合包验收。

### 3. featuresPerStep 何时求值？会不会注入前冻结？

原生 supplier 是懒的，validate 和 decoration 都可能触发（J-6）。**Lithostitched 在设置新 wrapper 后主动重置 supplier，并用它重建 feature 表**（J-5）。因此“提前求值后永远缺长城 features”的一般性断言不成立。

还要检查其它 mod 是否持有旧表、优化器是否跳过重置、完整 shared feature 图是否成环；这些运行组合 NOT_RUN。长城 runtime freeze 必须在最终注入完成后，不能把早期 generator 引用当冻结结果。

### 4. Region 完整写法及其“几何”含义是什么？

完整最小资源形状是：

```json
{
  "dimension": "minecraft:overworld",
  "biomes": "#minecraft:is_overworld",
  "weight": 100
}
```

路径 `data/<namespace>/lithostitched/region/<name>.json`。`name` 由资源位置绑定，codec 没有要求额外 name 字段（J-3）。

BiomeRegions 在某个本底 biome 可参与的 region 权重表中，用可选 region density function 的值选择 key；这可以空间变化，**但该 JSON 并不定义任意路线形状**。长城路线不能通过一个 HolderSet 或 weight 自动传进去。本方案不需要新增 region。

### 5. A1 可选 mod 树怎么自动生效、缺 mod 怎么跳过？

建议首选 **Fabric built-in datapack + 加载守卫**：

1. 主资源引用图只用原版；提供稳定的自家 tree-selection ID。
2. BOP/GoodEnding 的完整可选引用图放 `resourcepacks/<packid>/...`，含 `pack.mcmeta` 和替换的 selection/placed/configured 资源。
3. 初始化仅在 `FabricLoader.isModLoaded` 且 tree profile 已认证时注册对应 pack，使用 `DEFAULT_ENABLED`；用户仍可关闭。
4. 没装 mod 不注册该 pack，主包的原版 selection 仍在。装了 mod 但版本/完整写集不支持，明确诊断且不激活该可选 profile。
5. 两个树 mod 同时存在要固定选择/合并规则，不能靠 pack 同名覆盖的偶然顺序。选择纳入 recipe；进世界后变化拒绝 reload。

API 依据：[ResourceManagerHelper.java:75](D:/辅助源码/fabric-api/fabric-resource-loader-v0/src/main/java/net/fabricmc/fabric/api/resource/ResourceManagerHelper.java:75) 至 :92 的 `resourcepacks/<id path>` 与注册 API；[ResourcePackActivationType.java:22](D:/辅助源码/fabric-api/fabric-resource-loader-v0/src/main/java/net/fabricmc/fabric/api/resource/ResourcePackActivationType.java:22) 至 :34 的 NORMAL/DEFAULT_ENABLED/ALWAYS_ENABLED。具体调用需以项目锁定的 Fabric API 编译边界验证，NOT_RUN。

也可用 Fabric conditional overlay；[ResourceConditions.java:49](D:/辅助源码/fabric-api/fabric-resource-conditions-api-v1/src/main/java/net/fabricmc/fabric/api/resource/conditions/v1/ResourceConditions.java:49)、:54、:113..118 给出 `fabric:load_conditions`、`fabric:overlays`、`all_mods_loaded`。**必须条件化整个引用图**，不只是缺失树的单文件。仅改 `fabric.mod.json` 不能自动解决所有 JSON 的悬空引用。本报告推荐 built-in pack，暂不混用两套机制。

不要直接复用包含原 biome membership 检查的第三方 placed feature；可复用它的 configured tree，自建 wrapper/filter，并做完整树边界认证。

### 6. GreatWallBiomeRuntime 能否直接照抄 sampler-key 模型？

**不能直接照抄**，见 H2。writer 已拿到世界上下文，不需要绕回 sampler 猜世界。

建议 key 为 immutable `(runtimeSession, dimension, registryEpoch, recipeHash, chunkKey)`；value 为 immutable 已完成 mask/本底摘要，promise 单独纳入有限 lease 生命周期。CHM 是线程间入口，mutable builder/cursor/队列留各自 owner。只有 overworld 发布 mask。任何旧 callback、卸载或 reload 都校验 epoch；关闭等待实际生产者，不只移除 map。

不可用 `axis+AnchorField` 代替最终计划；也不可把 await-route 插进 source 采样，导致 oracle→biome→route→oracle 环。

### 7. QuartPos 精度与负坐标如何处理？

换算本身正确，不是负坐标 bug（J-9）：`-1 → quart -1 / local 3`。危险是手写 Java 整除和把群系边缘当硬保护边界。

固定 mask 量化规则，单测 `-17,-16,-5,-4,-1,0,3,4,15,16`、斜线、转角、四块交界与截断。身份边界容许 quart 级台阶，硬保护仍用完整精确 box。地表 Y 带同样需明确上下界及跨 section 规则，不复制全 Y writer。

### 8. 自己的矮树是否会被取消？怎么解？

**会**，如果 complete tree box 与 B4 的任何盒相交。源码没有命名空间例外，也不按“矮”直接放行。

保留 guard，景观 placement 先判断完整 box 在允许带，并调用原树路径。低矮树在无树核心外，高树更外侧；潜在出口、fort/tower、road approach 都排除。若要求 10/20 带里一定有树，则先裁决与现有保护的矛盾，不修改模板/guard 凑绿。

### 10. 道路留洞 / 截断成尽头路是否冲突？预留什么？

“截断道路”不等于删除任意现有墙块。不得改 S1A/S1B 几何或 ChunkPlanCompiler 负空间规则来完成此策略。双向真实调用与 GW-011 的相关矩阵仍要验证，本轮 NOT_RUN。
