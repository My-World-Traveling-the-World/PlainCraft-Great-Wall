## 2. 精确接入事实

- 实际本机 C2ME JAR SHA-256：`85de278c4acfddbaa748c1e72facaa7e13901f3980e5deb2c65ab7064fc8c460`。`D:\辅助源码\c2me` 是旧 0.3 系列，不能用它代替本机 0.27 的 ABI；本阶段核对的是本机 JAR 反编译与字节码。
- 实际目标有 `runTaskWithLockArea` 和 `SchedulingManager.positionedExecutor(long)`。ThreadLocal 订阅上下文在 `original.subscribe` **之前**建立；用 `doOnSubscribe` 会晚于 defer supplier，不能作为锁见证。
- `ModuleEntryPoint.enabled` 是常量 true，配置中没有 rewrite 总开关；`useLegacyScheduling` 不是关闭 rewrite。
- 关闭态采用已核实的 Fabric Loader `fabric.debug.disableModIds=c2me-rewrites-chunk-system,c2me-notickvd`，只在隔离测试任务启用。no-tick 模块的 metadata 明确依赖 rewrite。**C2ME 本体和 base 仍在，原 JAR 不改、不删除、不换版**。此态与完全未装 C2ME 单独记录，不是发行配置建议。
- 原版 `ServerChunkCache.getChunkFuture` 在主线程调用会执行 `managedBlock`。测试传送预热用已核实的 `getChunkFutureMainThread` invoker，返回 future 后退出 tick，再在完成回调中传送；没有在 tick 中等待它。
- Chunky 1.4.23 的 `onGenerationComplete` 在投递完任务后发出，不保证所有异步 chunk 已完成。测试改用 `GenerationProgressEvent.complete`，再验证目标 chunk 经过规划门，避免假阳性。

## 3. 正常与故障语义

正常测试必须同时具备退出码 0、`server-smoke-passed.txt`、CLOSED/futures=0 和相应注入记录；不能只看 Gradle 的 BUILD SUCCESSFUL。

FAIL、CANCEL 和 unresolved-startup 外部取消属于**预期启动中止**，必须没有 SERVER_SMOKE_STARTED/PASS，并包含真实原因和 CLOSED/futures=0。它们不是正常存档保存验收。

已发现并修复以下实际挂起路径：

1. 关闭 session 时同步抛出取消，可能绕过原版生成 future 的失败路径。改成 failed future，vanilla 成败都返回原 mailbox；STOPPING 时先存诊断，避免原版失败保存打断 STOPPED。
2. C2ME 记录规划错误后，出生搜索可能仍等未结束的 holder future。核实原版 nested chunk event loop 的 `throwIfFatalException` 后，将 BOOTSTRAP 失败接入 `MinecraftServer.setFatalException`，关闭所有规划租约并触发原版启动失败路径。保留首次超时和修复后的证据。
3. 已拒绝生成配方的 ACTIVE 世界再次请求冷区块时，C2ME 的同一 `MARK_BROKEN` 路径也可能挂起。`failRequiredPlan` 扩展到运行期必需依赖；错误处理包住依赖和原 continuation，而不只包住启动 lease。专门的真实区块用例已验证 `REQUIRED_PLAN_FAILED`、进程终止和 futures=0，不把“守卫方法直接返回 failed future”代替引擎实测。

测试框架另有两次纠正，早期失败证据保留：`jcmd` 在目标已经退出时可能自身挂住，已加独立 5 秒上限，回收前核对 PID/命令行，只结束取栈器；首次重载后冷区块测试没有保留票据，未到达规划门，不能算通过。改成保留普通 FULL 票据后验证了错误传播；这仅证明 S0-02 的正常加载入口，**不证明 S0-03 的 FEATURES-only PREPARE**。

故障中止可能出现 `Exception stopping the server`；C2ME 的异常启动进程也可能返回 0。报告不得据此宣称正常关服、完整保存或可继续使用该失败的测试世界。诊断入口仅用于隔离 S0 世界。
